第 01 节

个人 Agent 与记忆/上下文管理

长文件进上下文，贵的不是「模型看不懂」，而是先把整份 PDF、整本表格或整段录像都吃进去。今天的接口改动，是让 Agent 先粗读、再只加载真正用到的那几页。

Gemini API 上线文件切片：上传一次，按页、单元格或时间段加载，只对实际检视的部分计费

Rohan Doshi、Ben Caine（Google DeepMind） · Google · 标注 November 23, 2026 · 原文 博文加示例约 6–8 分钟

它说什么。 官方Gemini API 现在支持服务端文件切片：把 PDF、Office 与 OpenDocument 文档、表格、音频和视频直接交给接口，并指定只要哪些页、哪些单元格、哪一段媒介。官方写明，这样可以把上下文集中在相关部分，并且「只对 Gemini 实际检视的部分计费」。同一天还加上了 Microsoft Office 与 OpenDocument 格式的原生上传。该能力适用于全部 Gemini 4 模型；上传文件仍受原有体积和页数限制。

怎么用。 官方文件先经 Files API 上传一次，之后可以在多轮对话和工具调用里复用同一个 URI。Agent 也可以在函数返回（function_result）里直接指定要检视的部分。官方给的工作方式是：先用抽取文本、低分辨率预览或转写做廉价浏览，再只对图表、密集版式或关键帧花费高分辨率 token。文档和幻灯片可选页范围（start_page / end_page）、分辨率（low / medium / high）和内容层（page_text 或 page_image）；表格可选工作表和单元格范围，以及数据、公式与视觉层；视频和音频可按时间裁剪，视频还可调帧率和内容层（转写、帧或音频）。未指定处理选项时，文档和幻灯片默认使用保留版式的页面图像，表格则包含计算后的值、公式和所有工作表名称。

一个具体例子。 官方博文示例是：先把一份 Word 季报上传，用 Gemini 4 Hydrogen 只加载 page_text，问「收入桥图在哪一页」；再用同一个 URI，让 Gemini 4 Neon 以高分辨率只加载第 3 页的 page_image，去读那张图和脚注。官方的动机写得很直白：如果模型接口只能吞整份文件，Agent 往往要在客户端 harness 里跑 LibreOffice、PDF 渲染器和 ffmpeg，既占内存，也会在磁盘上留下抽出的帧。

局限。 博文提到合作伙伴已在生产 harness 里验证这些控件，但没有给出可核对的省 token 比例。切片能减少检视范围，并不能代替「先判断该看哪一段」；选错页或选错层，模型仍然看不到关键信息。现有文件体积和页数上限仍然有效。

短评。 评论这和「把 1M 上下文撑满再谈压缩」是两条路。对要处理合同、报表和长视频的个人 Agent 来说，先浏览、再定点加载，比再换一个更长窗口的模型来得更直接。它没有解决记忆写回，但把「这次推理到底该看见什么」从本地预处理收回到了模型接口。

是否值得读原文 · 值得。先看「先浏览再放大」的示例和各类切片参数，约 6 分钟。

Google 搜索的 Personal Intelligence 开始接入 Wallet；Drive 与 Gemini 应用将在未来数周跟上

Robby Stein（Google Search 产品副总裁） · Google · 标注 November 23, 2026 · 原文 博文约 4–5 分钟

它说什么。 官方Google 搜索的 AI Mode 开始支持把更多应用连到 Personal Intelligence。今天起可选择接入 Google Wallet，Drive 和 Gemini 应用将在未来数周跟进；它们将与已经支持的 Gmail、Calendar 和 Photos 一起，把消费、文档和对话中的个人上下文带进搜索。官方强调连接是选择加入，可随时在搜索设置里开关。接入 Wallet 后，AI Mode 只能读取账户信息，不能转移、管理或投资资金。未来还可以在定制回复下方通过「Personalization」图标查看所用上下文，并在对话里直接修正，例如说「我不再吃素了」。

局限。 这是消费级搜索个性化，不是可自托管的记忆系统；Drive 与 Gemini 应用尚未上线，博文也没有给出检索准确率或隐私评估的数字。Wallet 的「只读」是官方承诺，本文未独立核实实际权限边界。

短评。 评论它把「个人上下文」从聊天机器人里的记忆，推进到了搜索框。对关心个人 Agent 的读者，值得看的是产品选择：先连钱包和文档，而且把开关和可见的上下文来源写进界面；不必把它当成通用的跨应用记忆方案。

是否值得读原文 · 若在用 Google 搜索的 AI Mode，看完接入范围和开关说明即可，约 4 分钟。

第 02 节

RSI（自我迭代 / 人参与的迭代）

形式化验证给智能体团队加上了硬门：想法可以很大胆，但只有 Lean 通过的线路才会进入共享笔记本。

DeepMind：Gemini 4 智能体团队改进量子线路，并用 Lean 证明其正确；惯性约束聚变相关线路的计算代价降至约 1/11.8

Sergey Shirobokov、Ben Jaderberg、Ryan Babbush 等（Google DeepMind 与 Google Quantum AI） · Google DeepMind · 标注 November 23, 2026 · 原文 博文约 6–8 分钟；论文与 Lean 库另计

问题。 官方即便已有较好的量子算法，一些科学模拟对早期容错硬件仍然太贵。这些线路又很难在经典计算机或今天的小型量子处理器上直接试跑，因此需要数学证明来确认它们做对了。

方法。 官方他们对每个问题派出多支独立的 Gemini 4 智能体团队，去寻找算法改进。新想法先经 Lean 验证，再写入共享笔记本。每隔四小时，各队智能体会在一场虚拟会议里交换、辩论和比较想法。人负责选定问题和监督进度。官方同时开源了用于量子算法的 Lean 库、问题规格和已验证的解。

证据。 官方在惯性约束聚变的一项性质计算上，智能体团队把计算代价（量子比特与操作的综合度量）降为原来的约 1/11.8，所需容错量子比特从 5,650 降到 4,338。对一种常见光敏分子的模拟，代价降为约 1/8；对代谢大多数人类药物的酶细胞色素 P450，改进约 2.5 倍，内存从 481 降到 333 量子比特，方法是替换笨重的内存查找。他们还为一个具体实现的 Grover 算法给出 2.57 倍加速，并为把数值载入量子态时常用的 arcsin 例程给出 290 倍加速。官方宣布帖把总体改进概括为「最多约 10 倍」；分项数字以博文为准，其中 arcsin 的 290 倍高于这一概括。

局限。 官方这些改进后的算法，若要用于完整科学模拟，所需资源仍可能超过第一代容错量子计算机大概能提供的水平。数字是官方自报的线路资源，不是在真实量子硬件上测得的墙钟时间。开源库刚公布，本文只确认仓库存在，未复核其中证明。

短评。 评论值得看的不是又一个「智能体写代码」的演示，而是门禁：人出题，智能体搜索，Lean 决定哪一条想法能留下。它和周末那份黎曼猜想 Lean 证明走在同一条路上——形式化校验让人可以在尚未通读全部推理时，先确认语句和证明对得上。这里的 RSI 是人在环里的迭代，不是模型关起门来改自己。

是否值得读原文 · 值得。先读方法段和五组资源数字，约 6 分钟；若要核对证明，再下 GitHub 上的 Lean 库。

第 03 节

各领域模型能力进展

周末最重要的数学事件不在今日窗口里，但上一期没有写入；同一天的语音评测里，Phonic 1.1 在独立榜上接手了自己上一代的领先位置。

〔补记 · 11-20 / 11-21〕Alpöge 发布黎曼猜想的 Lean 证明；Lean FRO 与 Mathlib Initiative 声明对其正确性有充分信心

Lean FRO 与 Mathlib Initiative 联合声明 · 标注 2026-11-21 13:55 · 原文 联合声明约 5 分钟，Alpöge 短文约 8–10 分钟；17M 行 Lean 代码不适合通读

发生了什么。 官方/ 第三方11 月 20 日，Anthropic 的数学家 Levent Alpöge 发布了一份约 1,700 万 行的 Lean 库，认为自己在与 Claude 合作中发现了黎曼猜想的证明，并写明该方法容易推广到广义黎曼猜想。11 月 21 日，Lean FRO 与 Mathlib Initiative 发表联合声明，写明「我们充分相信 Alpöge 对黎曼猜想的证明是正确的」，并祝贺这一结果。声明说，社区按 四条标准 做了核验：所证命题就是 Mathlib 中已由专家审定的 RiemannHypothesis；该库可以正确编译，且多人复现了同一份原始证明导出文件；comparator 与 con-leche --compare 两个独立工具确认，库中证明的定理与 Mathlib 命题完全一致；导出后的惰性证明还经过 Lean 官方内核、con-leche、con-ron 以及若干用不同语言写成的第三方检查器复核，其中后两者带有相对于集合论的形式化证明，说明它们不能接受错误证明。

Claude 在其中的角色。 官方Alpöge 在短文里写，自己学生时代就计划用数十年走近这个问题；近几个月与 Claude 合作面很宽，「但这一次 Claude 在接近终点时远远超过了我」。他举了一个给同行看的细节：在函数域上 Stepanov 论证会用到带重数的除子，而在整数上「重数」很难找；Claude 建议，对长度为 X 的 von Mangoldt 和，theta lift 链的长度取 √X。他又写明：目前论证极长，自己只先提交 Lean，还没有写好可读的人工证明，并打算继续理解、讲解并简化它。他预期论证会被大幅简化。关于发布时间（Anthropic 上市次日），他写「精确的时机很糟」，并说若能更早完成会更好。

其他核对。 第三方Michael Rubinstein 的 Waterloo 页记录，11 月 21 日四项检查均无错误：全部 175,187 个模块可以编译；五个定理只依赖 Lean 的三条标准公理；用 Lean 内核重放全部模块均被接受；独立内核 nanoda 检查了这些定理所依赖的 1,484,729 个声明，无类型检查错误。该页提供脚本和日志，便于他人复现。MIT 的 Andrew Sutherland 也公布了核验文件与导出证明。联合声明核验的是黎曼猜想本身；Alpöge 还写到广义黎曼猜想，后一项不以 Lean FRO 声明为已背书。

局限。 机器核对确认的是：命题陈述正确，并且 Lean 证明就是这条命题。这不等于数学共同体已经读懂证明里的新想法，也不等于已有一份可审阅的传统论文。Alpöge 自己把目前文本写成「尚未掌握其周围一大片数学，就先把完整论证交出来」。17M 行代码不能当论文来读。媒体标题里的「AI 证明了黎曼猜想」容易把合作关系写成模型独自完成，短文本身并不是这样写的。

短评。 评论这是近年来最需要把用词收紧的一条。可核对的事实是：一份针对 Mathlib 标准命题的 Lean 证明，已经通过多个独立检查器。还没有被核对的，是证明为什么成立、能否被简化成人类可讲授的论证。Claude 在此是合作者，不是可以单独署名的作者。对关心模型能力的读者，它说明的是「形式化+强模型」已经能参与最经典的数学问题，而不是「读完新闻就可以宣布猜想已进入教科书」。

是否值得读原文 · 值得先读 Lean 联合声明和 Alpöge 短文，约 15 分钟。不要从通读 17M 行代码开始。

Phonic 1.1 发布；Artificial Analysis 语音对话指数给出 89.1，接替不到一个月前的 Phonic 1

Phonic · 标注 November 23, 2026 · 原文 产品博文约 6 分钟，AA 帖与榜单约 5 分钟

它说什么。 官方Phonic 在发布 Phonic-1 约三周后推出 Phonic-1.1，自称面向需要工具调用和复杂对话的语音到语音模型。第三方Artificial Analysis 在 11 月 23 日的帖子中写：Phonic 1.1（High）以 89.1 升至 Speech to Speech Index 第一，接替该机构不到一个月前为 Phonic 1 给出的 87.1。

分项。 第三方AA 写，Phonic 的优势在于带工具的客服模拟：在 τ-Voice 2.0 上，Phonic 1.1（High）为 87.1%，Phonic 1 为 85.6%，二者差距在误差范围内，但至少领先其他模型 5 个百分点。在 Speech Agent Arena 里，Phonic 1.1（High）与 Grok Voice 3.0 同为 1053 Elo（32 个模型中并列第 7），任务成功率为 92.9%，排第 3，落后于 Grok Voice 3.0 的 94.8% 和 Gemini 3.8 Live 的 93.2%。首音频时间平均 0.80 秒，高于 Phonic 1 的 0.61 秒，与 Grok Voice 3.0 的 0.81 秒相当，快于 GPT-Live-1（Astra，medium）的 1.34 秒。计价仍为每小时输入音频 4.20 美元（每会话分钟 0.07 美元），低于 Grok Voice 3.0 的 4.80 美元和 GPT-Live-1（Astra，medium）的 5.83 美元。Big Bench Audio 上为 99.5%，AA 注明该榜已接近饱和，前五名相差不到 1 分。

局限。 指数与分项都是独立榜或官方转述的第三方榜，不是用户环境里的通话质量保证。自然度与任务成功率并不是同一回事：Arena 偏好上它并未单独领先。首音频时间比上一代略慢。本文未试听该模型。

短评。 评论若关心语音 Agent，应看 τ-Voice 2.0 和任务成功率，而不是只看总分第一。它说明「会打电话办事」和「听起来更自然」仍可能分开涨。

第 04 节

世界模型 / 具身

今日没有新的世界模型评测，但有一项明确把「互联网视频预训练 + 在想象里练习」写成公司路线的融资发布。

Embo 出隐：Danijar Hafner 与 Wilson Yan 等人融资 1.1 亿美元种子轮，要用世界模型做机器人大脑

Embo · 标注 November 23, 2026 · Justine Moore、Raghu Raghuram、Matt Bornstein · Andreessen Horowitz · 标注 November 23, 2026 · 原文 两篇博文合计约 8–10 分钟

它说什么。 官方Embo 宣布要为智能机器人做「大脑」，让机器人在未见过的场景里开箱能用。官方判断是：今天的机器人技能仍脆弱，演示可以教会重复行为，却覆盖不了所有物体和情境；需要互联网规模的预训练来填任务之间的空隙，再用练习培养可靠的动作技能。世界模型被写成这条路的关键：先从大量互联网视频里学习物体、物理交互和任务如何展开，再在多样的想象情景里练习动作，以应对真实世界中的意外。公司要做的是一个统一模型，从头做互联网规模预训练，再在其人形机器人车队的经验上微调，并用强化学习做后训练。种子轮规模为 1.1 亿美元，由 Andreessen Horowitz 领投，Khosla Ventures、DST Global、NVIDIA（NVentures）及其他战略投资者参与。

团队与背景。 官方创始人包括 Danijar Hafner 与 Wilson Yan。官方列举的先前工作有 Dreamer、VideoGPT 和 Diffusion Forcing，经验来自 Google DeepMind、Meta Superintelligence Labs、NVIDIA Cosmos、UC Berkeley 和 MIT。Embo 还写，团队曾搭建在 70,000 块 GPU 上训练多模态模型的基础设施；这是对既往经验的自述，不是对 Embo 当前算力的说明。a16z 的文章把 Hafner 的路线概括为：世界模型提供物理知识，在模型内部的练习把知识变成技能，从而让机器人学习可以随算力扩展，而不只依赖在真机上采集的演示。

局限。 这是公司成立与融资声明，没有公布可核对的真机成功率、对照基准或产品发布时间表。a16z 写「早期结果相当令人鼓舞」，但未给出数字。互联网视频能否迁移成可靠的机器人动作，仍是开放问题，官方自己也把泛化和抗干扰写成尚待解决的两件事。

短评。 评论它把近年来世界模型研究里反复出现的两句话写成了公司命题：用视频学习「世界怎么运作」，再在想象里做强化学习。对关注具身和世界模型的读者，价值在路线声明，不在今天能下载一个更强的控制器。

是否值得读原文 · 值得读 Embo 公告和 a16z 投资说明里关于「演示很脆、在想象里练习」的段落，约 8 分钟。不要把融资规模读成能力已经达到。

第 06 节

高效使用 AI / Agent

写代码的速度，已经快过把 PR 送过审查、修复和合并。Claude Ship 把这后半段收成一套可按仓库打开的智能体。

Anthropic 推出 Claude Ship：审查、修复并按团队策略批准 GitHub PR；PR Steward 与 Approvals 为测试版

Anthropic · 2026-11-23 · 原文 公告约 8–10 分钟

它说什么。 官方Claude Ship 今日以测试版面向 Claude Team 和 Enterprise，用于 GitHub 仓库。它由已经正式可用的 Code Review，以及两个测试版智能体组成：PR Steward 和 Claude Approvals。目标是把审查、修复和批准决定连起来，让团队不必手工管理每一步。开发者也可以在 Claude Code 里运行 /ship：推送改动、打开 PR、处理反馈和失败检查，最终能否合并仍取决于该开发者的权限和仓库分支规则。管理员可以按仓库打开 Code Review 和 PR Steward，选择 Quick / Standard / Deep 审查级别、何时运行审查，并设置花费上限。Claude Approvals 在默认分支上存在策略文件时开始工作，也可被关掉。官方建议多数客户先在只观察模式上运行批准策略，再把它接入分支保护。

各部分做什么。 官方Code Review 从多个角度审查 PR，收集发现、对抗性核验、分类，再发到 PR 上。PR Steward 负责让 PR 保持通过，但被设计为不批准、不合并；它会处理失败的 CI、合并冲突，以及来自 Code Review、其他审查工具或同事的反馈；每次推送后会评论改了什么、如何撤销；开发者可用 @claude 给指令，或用 @claude stop 让它停下。Claude Approvals 读取仓库里的策略文件，对策略允许的常规改动可以自行批准，也可以要求更深入的人工签字，官方把它比作更聪明的 CODEOWNERS。

官方给出的使用数字。 官方在 Claude Code 团队内部，Claude 的审查是更广流程中的一层：6 月到 9 月，已合并 PR 数量增加了一倍以上，被回退的比例下降了 40% 以上。这是 Code Review 已在使用中的内部观察，不是对新测试版 PR Steward / Approvals 的对照实验。符合条件的 Enterprise 组织可领取至少 10,000 美元的 Claude Ship 额度，需在领取后 30 天内使用，领取截止日期为 2027 年 1 月 15 日，具体以条款为准。计费按 token：打开 Ship 会增加组织费用；Claude Approvals 没有基础费用，但策略里的分类器按 token 计费，若策略触发 Claude 的审查，即使在观察模式也会产生 Code Review 费用。/ship 计为常规 Claude Code 用量。对采用 Zero Data Retention、HIPAA 配置或客户管理加密密钥的组织，Claude Ship 不可用。

局限。 目前只支持 GitHub，且仅限 Team / Enterprise。内部「合并数翻倍、回退下降」没有公布仓库范围、PR 类型和对照方式。批准智能体仍是测试版；官方自己也把先观察、再接入分支保护写成推荐路径。

短评。 评论它针对的是一个很具体的瓶颈：模型已经能写大量代码，但审查、修 CI 和合并仍要人盯着。和「再做一个会写代码的 Agent」相比，更值得看的是权限设计——Steward 不批准、Approvals 读仓库里的策略、管理员按仓库开关。这和「只做审查、不改代码」的角色约束是同一类工程问题。

是否值得读原文 · 若在用 Claude Code 或管理 GitHub 仓库，值得读完工作方式和限制条款，约 8 分钟。

今日的系统层发布，是给防御者一段「补丁还没打上、服务又不能停」的窗口。

OpenAI 与 Cisco 开源 Shirudo：用 eBPF 在不停机的 Linux 系统上部署经批准的防护

OpenAI · 标注 November 23, 2026 · 原文 OpenAI 博文约 6–8 分钟

它说什么。 官方OpenAI 与 Cisco 推出开源运行时 Shirudo（日语「盾」）。它面向这类情况：发现漏洞之后，测试和部署补丁仍可能要数天或数周；若直接封禁某个 Linux 操作，又可能把合法请求一起挡掉，导致服务停机。Shirudo 让安全团队先测试一道临时防护（官方称为 shield）是否只挡住暴露漏洞的行为、同时放行合法请求；操作员批准后，可以在服务继续运行时部署。官方列举四项能力：在不停机的情况下用 eBPF 挡住易受攻击的代码路径，并可先观察再强制执行；为智能体提供可编程接口，去调查漏洞、生成定向防护并在攻击和真实负载上验证，但部署仍由安全团队控制；防护在加载前经过加密签名和校验，并经过 Linux 的 eBPF 验证器；用 TPM 记录防护的加载与移除，便于事后核对。

一个受控试验。 官方在受控测试中，团队用 OpenAI Codex 生成一道防护，给 Java 的 Base64 解码器加上输入检查，并挂到正在运行的 Elasticsearch 进程上。在利用 Java4Shell 的尝试中，该防护拒绝了恶意输入，攻击被挡住，Elasticsearch 继续运行。官方邀请开发者、安全研究者和基础设施运维共同改进该项目。

局限。 这是受控试验中的一次演示，不是大规模生产部署报告，也没有给出漏报、误杀或性能开销的统计。智能体可以提议防护，但官方把批准权留在操作员一侧；若批准流程被绕过或签名密钥管理失当，风险会转向部署环节。本文只确认项目站与 GitHub 仓库存在，未审计其内核组件。

短评。 评论它把「Agent 写防护」放进了必须由人签字、由内核验证器约束的轨道里。对做 Agent 落地的人，值得看的是这套批准和取证设计，而不是把一次 Java4Shell 演示读成通用自动防御已经可用。

是否值得读原文 · 值得读 OpenAI 博文里的四项能力和 Java4Shell 例子，约 6 分钟。若要动手，再看项目站和仓库。
