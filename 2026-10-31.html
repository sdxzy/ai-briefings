DeepSeek Super-agent：Router–Worker 怎样让 Agent 持续在线并行干活

DeepSeek 产品部 / Harness 团队 · 2026-10-31 · 原文 设计文章约 25–40 分钟；原型 README 另需 10 分钟

发生了什么。 官方文章写明「并非对现有产品功能的介绍」。定位是挂在 DeepSeek Harness（Cordis 插件内核）之上的调度/运行时：把「对用户连续」和「对任务并发」拆开。目标四特征：连续（多入口像同一个 Agent）、高效（可并行）、主动（听环境事件）、持久（可恢复）。作者认为单个经典 ReAct Loop 撑不住这四项。

核心设计。 官方

  • Router–Worker： Router 只交互与分派，可用更轻模型；Worker 隔离执行、不直接对用户说话，通常最强模型 + 完整工具。Router ≠ Team Lead：前者管任务之间，后者拆一个复杂任务内部。
  • 事件路径： Trigger → Fast Path（规则）→ Slow Path（LLM 策略）→ Router 分派；已订阅 Thread 可直通 Worker。消融显示去掉直通后完成时间几乎不变，但 Router 决定数约 +30%、读缓存 token 约 +37%。
  • 上下文： Inline & Spill 把窗口当 Cache；Chain of Recall 用 ID 引用链跨信道找回旧任务。
  • 异步 ReAct： start()/stop()，结果事件回灌；Harness 已实现，默认未开。
  • 存算分离 + BYOM： 云端无状态 Loop + 端侧 daemon 执行；优先接用户本机。
  • Watchdog： 主系统外的独立 Session，盯故障与空转。

实验（作者标注：合成负载，初步参考）。 官方约 300 条消息 / 约 20 条工作请求。Super-agent 完成时间 p50/p95 约 12.4 / 15.7 分钟，优于单 Session+Subagent（中性提示 20.4 / 29.5；优先委派提示 13.8 / 29.0），但读缓存 token 更高（约 23M vs 6–11M）——用更多 token 换更稳的调度。

原型与安全。 官方原型面向单个 GitHub 仓库的主动 Coding Agent；Worker 以操作者 OS 用户身份跑命令且无审批，需隔离环境 + 专用账号。官方承认最硬的开放问题是安全与隐私：云端 Loop 被注入后的端侧全控、凭据进上下文。

评论和 Harness² / GEPA 互补：Super-agent 管「怎么组织活着的多 Agent 系统」；后两者管「怎么把单个 harness / 提示词变好」。

是否值得读原文 · 值得读 Router–Worker、事件路径与实验表；安全与 BYOM 两节对自建常驻 Agent 直接有用。原型 README 的隔离警告必读。
