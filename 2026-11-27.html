第 01 节

个人 Agent 与记忆/上下文管理

窗口满了就摘要历史，是现在多数 Agent harness 的默认做法。今天有两篇论文分别问：能不能让模型自己决定压什么，以及记忆已经在提示里时，模型会不会照样答错。

NVIDIA：把压缩上下文的决定交给模型；GPT 6.1 在 32K 预算上，OfficeQA Pro v2 从 21% 升到 56%

Alessio Devoto、Avinash Vem、Tara Safavi 等（NVIDIA） · arXiv:2611.34147 · 11 月 26 日（Thu）批次 · 原文 摘要与设定约 8–10 分钟；对照实验约 20 分钟

问题。 论文长程 Agent 的工具调用、输出和对话会把上下文窗口填满。现在的常见做法是：窗口快满时，由 harness 触发一次压缩，把历史收成摘要。作者把这种做法称为 harness 驱动的上下文管理。问题是：该留哪一段、该摘要哪一段、该在什么时候动手，并不总是「满了再压」这一条规则能决定的。论文要问的是：如果把这些决定交给模型，任务成绩会不会更好，推理引擎能不能把这种编辑做得更便宜。

方法。 论文作者在 NVIDIA 的开源 Agent harness NOOA 里给模型提供一套 context API，由模型决定何时、对哪一段做压缩。对照是 harness 在窗口满时自动压缩。评测覆盖文档研究和机器学习工程，上下文预算从 8K 到 512K。他们还测试了推理引擎在模型改上下文之后，能否复用未被改动的后缀 KV cache，以降低预填充（prefill）计算。

关键数字。 论文在 32K 预算的 OfficeQA Pro v2 上，由模型自己管理上下文时，GPT 6.1 的分数从 21% 升到 56%。文中还写，Kimi 在提高准确率的同时，最多可少用 41% 的输入 token。模型之间差异很大：调用 API 的频率、压缩的激进程度、以及何时开始压缩都不一样，而且改一点提示就会改变这个时机。推理侧，复用编辑后未改动后缀的 KV cache，单次请求的预填充计算最多降约 15%，作者称准确率没有可测到的变化。

局限。 这是预印本，数字绑定在所报告的任务、模型和预算上，不能外推成「所有 Agent 只要把压缩交给模型就会接近三倍」。作者自己也写，不同模型用 API 的方式差得很远，提示一变，压缩时机就变。KV cache 复用节省的是预填充，不是生成；而且 15% 是上限。

短评。 评论这和近日简报里「该记多少、该不该把历史滚成一份摘要」是同一类问题，只是把决定权从规则移到了模型。例子清楚，32K 预算上的对照也够用来判断自己的场景。方法并不复杂，不必单独做深挖；更值得记下的是：上下文管理正在变成模型和推理引擎要一起设计的接口，而不只是 harness 里的一段脚本。

是否值得读原文 · 值得读摘要、两种策略的对照和 32K 预算那一组数字，约 10 分钟。不必先从推理引擎的实现细节读起。

Letting Models Manage Their Own Context: Where We Stand (arxiv.org) NOOA (github.com)

TASK Memory：记忆已经放进提示，模型仍可能不用或用错；在十组设定里，忽略记忆的比例降到不超过 1.5%

Jinkun Zhao、Wenjun Wu（北京航空航天大学） · arXiv:2611.34762 · 11 月 26 日（Thu）批次 · 原文 摘要与错误分类约 8–12 分钟；方法与表格约 25 分钟

问题。 论文Agent 常常依赖外部记忆，但答错不一定是没取到。正确的记忆已经检索出来、放进了提示，回答却和它矛盾，或者把这段记忆安到了别的问题上。作者把这类错误称为使用时的记忆幻觉（use-time memory hallucination）。一个具体情形是：用户上周把地址改了，记忆库里有新地址，模型却仍报训练数据里的旧地址；或者把甲的偏好说成了乙的。

方法。 论文作者在五个开源模型上观察这类错误，并把它分成三种：忽略记忆（回到权重里的旧事实）、用错对象（把记忆安到相邻实体上）、版本混淆（新旧两个版本都在，却坚持过期的那个）。他们提出 TASK 记忆：一段记忆不只是文本，还带一组可移除的知识编辑，以及一对激活引导向量。文本保存内容；知识编辑提供地址，并支持多跳组合；引导向量不写入新内容，只在本次查询里决定模型是采用这段记忆，还是坚持自己的答案。实验在冻结的现成模型上进行，并采用预先登记、只测一次的协议。

关键数字。 论文在所报告的设定里，忽略记忆最多约占查询的 46%；用错对象最多约 24%，在检索再叠加权重编辑后最多约 49%；版本混淆中，约 53% 的回答仍断言已被替代的旧值。TASK 在全部十个模型–数据集组合里，把忽略记忆的比例降到 不超过 1.5%；在 CounterFact 上，把邻居误用从 39.2% 降到 7.5%（文中称复合指标提高 10.8 个百分点）。在 300 条记忆的库上，它比 BM25 RAG 高 16.4 个百分点，这一优势在 3,000 条时仍然存在；在 MQuAKE 上，多跳准确率提高 7.5 个百分点。作者称，8B–27B、四个模型家族的 23 组跨模型比较中，有 21 组显著，并且在 10 组里有 9 组超过三种近期的上下文引导方法。

局限。 这是预印本，方法依赖知识编辑和激活引导，部署成本高于「只往提示里塞文本」。评测以事实性记忆和特定数据集为主，不能直接等同于跨会话的个人偏好或长任务状态。上限数字（46%、49%、53%）是「最多达到」，不是平均水平。

短评。 评论它把问题从「有没有取回」推进到「取回了会不会用」。和上一则形成对照：上一则关心窗口里该留什么，这一则关心留对了模型会不会照着做。分类清楚，表格也够用；方法偏专门，不必当成通用记忆系统来深挖。

是否值得读原文 · 值得读三种错误的定义和主要表格，约 10 分钟。若你不打算在权重里做编辑，可以不读实现细节。

TASK Memory: Beyond Text-Only Memory with Activation Steering and Knowledge Editing against Memory Hallucination (arxiv.org)

第 02 节

RSI（自我迭代 / 人参与的迭代）

记忆系统的行为，往往不取决于又换一个模型，而取决于写入、维护、取回和回答那一套代码、提示和配置，也就是 harness。今天有一篇论文试图自动改这一层。

HoMe：用评测结果迭代改记忆系统的 harness；在 BEAM-1M 上比原 harness 高 5.4 个百分点，查询时 token 约少 41%

Yifei Xu、Li Yu、Zhaoyang Liu 等（上海交通大学、阿里巴巴、北京大学） · arXiv:2611.34624 · 11 月 26 日（Thu）批次 · 原文 摘要与实验设置约 10 分钟；结果与附录约 25 分钟

问题。 论文一个长期运行的助手要把跨会话的经验变成以后还能用的行为，通常会有一套记忆系统。真正起作用的，往往是它的 harness：负责记忆构建、维护、检索和回答生成的代码、提示和配置。改这一层至今多半靠人手。作者指出，允许任意编辑，也不等于会得到结构性的改进——在他们的对照里，另一种自动方法 MemPro 虽然允许改可执行代码，提出的候选却都只改了提示或参数。

方法。 论文HoMe 按评测结果迭代：每次从已经评过的 harness 出发，编辑其中任意部分，得到新的候选。它用会话级的记忆版本和执行轨迹，把多条失败归到共同机制，并定位到相应的会话和组件。为了控制成本，它用候选门控、冒烟测试、自适应抽样，并复用已经构建好的记忆。作者在开源系统 ReMe 上验证，每个基准在完整的初次评测之后，再做六次正式的候选评测。训练集和测试集分开：LongMemEval-S 的 500 条案例对半划分，平均历史约 115K token；BEAM 在 BEAM-100K（20 个案例）上优化，在 BEAM-1M（35 个案例、每个 20 个查询，平均历史约 1.04M token）上测试。

关键数字。 论文相对原来已经较强的 harness，HoMe 找到的版本在 LongMemEval-S 上高 2.8 个百分点，查询时 token 少约 59%；在 BEAM-1M 上高 5.4 个百分点，token 少约 41%。与 MemPro 相比，LongMemEval-S 高 10.4 个百分点、token 少约 81.5%，BEAM 高 1.1 个百分点、token 少约 7.6%。作者报告：BEAM-1M 的分数提升显著（配对 bootstrap 95% 区间 [0.028, 0.082]，p=0.0002），token 下降也显著；LongMemEval-S 上 2.8 个百分点的分数提升不显著（95% 区间 [-0.016, 0.072]，p=0.25），但 token 下降显著（每查询约少 26,057 token，合 59.3%）。在 BEAM-100K 上优化的 harness，用到平均约长 8 倍的 BEAM-1M 对话时仍然有效。

局限。 这是在 ReMe 和两个基准上的预印本结果，不能直接说成任意记忆产品都会同样涨分。LongMemEval-S 的分数提升本身站不住统计学门槛，更稳的是省 token，以及 BEAM-1M 上的那 5.4 个百分点。BEAM 的案例数也不多（训练 20、测试 35）。优化循环仍然要跑多轮评测，只是作者把成本压到了「每个基准六次正式评估」。

短评。 评论它和上一节的 NVIDIA 论文是互为补充的：一个把「压什么」交给模型，一个把「整套记忆流程怎么写」交给评测循环。对已经在用文件型或开源记忆系统的人，附录里改了哪些机制（例如事实级索引、带来源的检索）比框架名字更有用。方法是标准的评测驱动搜索，不必单独做深挖。

是否值得读原文 · 值得读摘要、两个基准的协议，以及作者自己报告的显著性，约 10 分钟。LongMemEval-S 那 2.8 个百分点不要单独当结论。

HoMe: Toward Practical Harness Optimization of Memory Systems for AI Assistants (arxiv.org) ReMe (github.com)

今天没有新的通用旗舰模型发布。语音和方言是窗口内比较具体的一项官方更新。

通义千问：Qwen-Audio-3.1 扩展多语言和方言；官方称 ASR 覆盖 59 种语言和 8 种中国方言

11 月 26 日 · 原文 原帖约 2 分钟；产品页约 5 分钟

它说什么。 官方Qwen 写道，Qwen-Audio-3.1 系列此前已经发布，当天带来增强的多语言能力，并特别强调中国方言。官方列出的覆盖范围是：ASR 为 59 种语言、8 种中国方言；TTS 为 65 种语言、6 种中国方言；Realtime 为 53 种语言、6 种中国方言。帖中强调方言识别与合成有所增强，并给出三个 Flash 产品页。

第 04 节

世界模型 / 具身

通用 VLA 在分布内往往很顺，一换位置或加长程推理就掉得很快。今天有一篇论文把「先用 Agent 找补丁，再把补丁练回策略」写成一个闭环。

RoboEvo 2：让机器人的 harness 与策略互相迭代，而不再额外收集人工演示；LIBERO-PRO 上独立成功率从 11.0% 升到 84.1%

Zhongrui Wang、Xiaojuan Qi 等（香港大学、浙江大学、南方科技大学） · arXiv:2611.34675 · 11 月 26 日（Thu）批次 · 原文 摘要与两段循环约 8–12 分钟；实验部分约 20 分钟

问题。 论文机器人既要在陌生环境里想出办法，又要在学会之后流畅执行。视觉–语言–动作（VLA）策略执行快，但遇到没见过的布置，往往还要再收人工演示。推理 Agent 可以调用控制接口去试、去修，但每一步都要再想一遍，延迟和接口费用都高。作者用一个常见反差来说明：策略在标准任务上可以很强，一旦场景或物体位置变了，成功率会掉下来。问题是：能不能在不再收集新的人工演示的前提下，让系统自己找到补丁，并逐步把补丁变成更便宜的策略？

方法。 论文RoboEvo 2 把这一过程写成 harness 与策略的双向进化。在策略到 harness（P2H）方向，策略失败会引导编码 Agent 搜索三种路线（代码、代码加上下文示例、代码加策略），并把验证过的解法沉淀成可复用技能、路由策略和经验记忆。在 harness 到策略（H2P）方向，验证过的轨迹做监督训练，同时用反事实偏好蒸馏（Counterfactual Preference Distillation）：从同一起始状态出发，让策略更偏好成功的修正、而不是失败动作。改进后的策略为下一轮搜索提供更好的动作，剩下的失败再送回 harness，形成循环。

关键数字。 论文在不再额外收集人工演示的前提下，作者报告 LIBERO-PRO 上独立成功率从 11.0% 升到 84.1%，混合成功率从 30.4% 升到 90.5%；在 RoboTwin C2R 上也有类似提升，并降低了 Agent 侧成本。文中还报告任务可被自主获取、harness 可跨本体迁移，以及在 Unitree G1-D 上混合成功率为 95.0%。

局限。 这是预印本，LIBERO-PRO 等主要数字来自仿真；真机只报告了 G1-D 上的混合成功率，不能把 84.1% 或 95.0% 读成已经可部署的工厂指标。这些数字是在作者的协议下、相对他们自己的起点得到的，不是对所有 VLA 的通用涨幅。代码仓库已经可以打开，但「将公开发布」仍以仓库当时内容为准。

短评。 评论它把第 2 节 HoMe 的思路搬到了机器人：先改 harness，再把验证过的行为蒸馏回策略。涨幅看起来很大，所以更要先看起点有多低、评测是不是仿真。对关心世界模型和具身闭环的人，两段循环的设计比单一分数更值得看。

是否值得读原文 · 值得读摘要和 P2H / H2P 两段循环，约 10 分钟。先把仿真和真机数字分开，再决定要不要看实验细节。

RoboEvo²: Recursive Robot Self-Improvement via Harness-Policy Co-Evolution (arxiv.org) RoboEvo2 (github.com)

第 05 节

AIGC 视频生成

离线多镜头生成可以先读完整剧本、再计划、失败就重拍；直播式生成做不到这一点。今天有一篇把记忆 Agent 接到实时长视频上的论文。

Agentic LongLive：给实时长视频加一套异步的实体记忆；相对基线，主角身份一致性提高 44.9 分，重访地点提高 40.4 分

Shaoteng Liu（香港中文大学）、Shuai Yang、Wei Huang、Luozhou Wang、Song Han（NVIDIA / MIT）、Yukang Chen（NVIDIA） · arXiv:2611.34907 · 11 月 26 日（Thu）批次 · 原文 摘要与设定约 8–10 分钟；基准与系统结果约 20 分钟

问题。 论文实时自回归视频生成已经可以连续输出数分钟，并在中途接受新提示，但人物、物体和地点在较长的互动故事里仍容易对不上。现有的 Agent 记忆多半用于离线多镜头：事先读完全部剧本，先规划再生成，失败就重拍。直播式生成做不到这些——下一句提示要到该镜头开始时才出现，也不能让画面停下来等记忆系统。

方法。 论文Agentic LongLive 把记忆 Agent 放在单独的 GPU 上异步运行。它只读取到目前为止已经出现的提示，不读取已生成的视频，并为每个人、物、场景维护文本状态和不断更新的图像。它据此合成一张全局图和每镜的记忆图，由辅助 GPU 在下一镜开始前预填进生成器的 attention sink，同时为被点名的实体写实体卡片。这样生成不必等待记忆，视频错误也不会被写回记忆。一个用强化学习训练的小语言模型负责在下一条提示到来之前决定该记住什么，其图像奖励用下游视频结果校准。评测用新基准 LongStory-Online：25 个故事、共 857 个镜头，每次只揭示当前这一镜。

关键数字。 论文相对基线生成器 LongLive-2.0，Agentic LongLive 把持久状态准确率提高 26.3 分，主角身份提高 44.9，重访地点一致性提高 40.4；在 H100 上额外生成时间约 1%。作者称，完整系统在一台 8×B200 节点上以 BF16 运行生成器时为 34.3 FPS，快于实时；在约 14 分钟的故事里图像质量保持稳定，并且在两个 MiniMax-H3 生成器上也改善了身份一致性。文中称，就他们所知，这是首个由 LLM Agent 同时维护文本和图像记忆的实时视频生成器。

局限。 数字主要来自作者自己的 LongStory-Online 基准和指定硬件，不能直接换成其它生成器或其它故事类型的通值。「快于实时」绑定在所报告的节点和精度上。记忆 Agent 故意不看生成画面，因此画面里已经出现的偏差，不会自动被写进记忆去纠正。

短评。 评论对做长视频或短剧、又在意人物和场景回访是否对得上的人，这条比又一个单镜画质对比更有用。它把「记忆」写成生成管线里的前置条件，而不是事后修图。方法清楚，不必把全部系统配置都读完。

是否值得读原文 · 值得读摘要、记忆与生成如何错开，以及 LongStory-Online 的协议，约 10 分钟。

第 06 节

高效使用 AI / Agent

长上下文和 Agent 工作负载里，解码往往最慢。投机解码可以少跑几次目标模型，但草稿模型自己再做一套检索，成本又会回来。

腾讯混元开源 DFly2：草稿模型复用目标模型已经选好的稀疏位置；官方称长上下文和 Agent 任务上最高约 4.2 倍加速

Hong Liu、Guanghua Yu 等（腾讯） · arXiv:2611.34776 · 11 月 26 日（Thu）批次 · 原文 原帖约 2 分钟；论文摘要约 8 分钟

问题。 论文DeepSeek-V4、Hy4 这类模型已经用原生稀疏注意力来避开长上下文上的二次代价。投机解码可以再减少目标模型的前向次数，而且对质量无损，这在长上下文解码最慢的时候最有用。但现有的块并行草稿模型，仍常为自己保存一套上下文缓存，或者再做一次位置选择。目标模型压缩得越狠，草稿侧那份缓存占的比例就越大；如果草稿再按查询重新打分，成本又会随上下文变长。

方法。 论文DFly2 让草稿层直接读配对目标层已经缓存的 KV，并只用该层索引器已经选好的位置（固定数量，可来自上下文各处）。这样草稿模型不再自己打分，也不再单独存一份缓存。作者在三种稀疏结构和架构不同的目标模型上评测：DS-V4.1-Flash、GLM-5.3-Flash 和 Hy4 flash，覆盖通用、长上下文和 Agent 基准，并使用两个温度。

关键数字。 官方混元在宣布帖中称，DFly2 是 Hy4 flash 的投机解码草稿器，长上下文和 Agent 工作负载最高约 4.2 倍加速；草稿成本不随上下文变长，也不额外占用 KV 内存。官方还写，在 Agent 任务上比同一配方的 DSpark 大约快 30%，比开源 DSpark 多接受 10.4% 的草稿 token。论文在同一训练配方下，DFly2 每步接受的 token 多于 DFlash 和 DSpark；相对较强基线的优势，在通用负载上为 3.9%–10.5%，在最长 128K 的长上下文和 Agent 负载上扩大到 10.0%–31.5%。在高并发、且把每用户解码速度对齐的条件下，服务 DS-V4.1-Flash 时，它在 64K 的长上下文和 Agent 集合上分别比该基线多提供 62% 和 81% 的吞吐。

局限。 4.2 倍是官方给出的上限，不是所有负载的平均值。论文中的百分比较的是接受率和吞吐，比较对象和并发条件都写在原文里，不宜和官方「最高 4.2 倍」混成一个数。目前公开的是针对特定稀疏目标模型的草稿器，不是对任意稠密模型即插即用。

短评。 评论如果你已经在用 Hy4 flash，或同类原生稀疏的长上下文模型跑 Agent，这是今天最具体的推理加速更新。核心想法很清楚：目标模型已经付过选择位置的代价，草稿不必再付一次。

是否值得读原文 · 先看官方帖和论文摘要，约 8 分钟。若要核对 4.2 倍出现在哪一组负载，再读实验表。

第 07 节

模型发布与评测、AI 产品与落地

开源侧今天有一个完整的新权重系列；订阅产品侧则是一次已经影响用量的计费更正。

Sber 发布并开源 GigaChat 4：708B 总参、41B 激活，原生 100 万上下文，MIT 许可；官方自报 Terminal-Bench 2.0 推理模式为 71.26%

26 Nov 2026 · 原文 摘要约 8 分钟；技术报告全文较长，评测表约 15 分钟

它说什么。 官方GigaChat 4 是 708B 总参数、每 token 激活 41B 的混合专家模型，接替 432B 的 GigaChat 3.5，原生上下文长度为 100 万 token（模型卡写明最大 1,048,576）。架构在 GigaChat 3.5 的混合主干上，为多头潜在注意力加入 DeepSeek Sparse Attention（DSA），并与 Gated DeltaNet 按 3:1 交错：线性注意力 48 层，稀疏注意力 16 层；256 个路由专家中每次激活 8 个，另加 1 个共享专家。和 3.5 不同，推理（Reasoning）与即时（Instant）两种模式做在同一个检查点里，可按请求选择。监督微调之后，先用强化学习训练专科模型，再用多教师在线蒸馏合并到一个模型中。权重以 MIT 许可发布，提供 FP8、BF16、GGUF、基座和中间检查点。

关键数字。 官方技术报告摘要写，在其评测协议下，GigaChat 4 在 Terminal-Bench 2.0 上推理模式为 71.26%、即时模式为 60.47%；对应的 GigaChat 3.5 为 30.30% 和 12.94%。这些是官方自报，而且报告写明：部分基准使用了他们自己实现的评测程序，有的项目把超时提高到七小时。不宜把这些数字直接当成与其它实验室公布成绩可严格对齐的独立榜。

局限。 截至撰写时未见同一协议下的独立复现。708B 总参、BF16 权重要求很高的显存，模型卡也写明了多节点部署条件；开源不等于能随手上线。对长上下文和 Agent 成绩，应等待独立评测，而不是只看对 3.5 的自比提升。

短评。 评论这是窗口内最完整的开源权重发布：许可宽松，上下文和两种模式的设计也很清楚。对要跑本地或可控推理栈的人，先看技术报告摘要和模型卡即可；对日常订阅产品，它还不能替代你正在用的封闭模型，除非你打算自己部署。

是否值得读原文 · 值得读摘要、架构表和 Terminal-Bench 那一行，约 10 分钟。交叉对比其它模型的大表，只适合当「官方自报」来看。
