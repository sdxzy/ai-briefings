第 01 节

个人 Agent 与记忆/上下文管理

把经验写成指南很容易，难的是：同样一份记忆，对不同强弱的模型并不是同一剂药。

IBM 部署实验：该记多少是模型的属性；强模型吃全量指南继续涨，弱模型用约 29 条反而比 199 条更好

K. R. Jayaram、Vatche Isahagian 等（IBM） · arXiv · 星期五（11-20）新公告 · 原文 摘要、AppWorld 对照与部署教训最有用，约 12–15 分钟

问题。 论文作者阅读了 IBM CUGA 与 AppWorld 参考 Agent 的大量轨迹后认为：长程任务上的失败很少是「不知道 API」，而更多是程序性疏漏——翻页翻错、实体解析错、没被提问却给出答案，而且这些错误会反复出现，因而看起来可以从自身历史里学会。

方法。 论文流水线分三步：先从 Agent 自己的轨迹里挖掘短教训，每轮 1–3 条；再把教训合并成更小的指南集，每条指南记录它合并了多少条教训；推理时把全部指南或筛选后的子集交给 Agent。流水线开源在 altk-evolve 库中，并已部署到 IBM 的 CUGA Agent 与 watsonx Orchestrate。主评测是 AppWorld，覆盖任务完成率基线约 40%–92% 的多种模型。

证据。 论文中心结论是：合适的记忆量是模型的属性，而不是记忆系统的属性。强模型会随着指南增加继续提高：DeepSeek-V3.2 使用全部 191 条指南时，任务完成率提高 9.5 个百分点，场景完成率提高 16.1 个百分点。弱模型则不同：gpt-oss-120b 基线任务完成率为 39.9%，用上全部 199 条指南升到 51.2%，但用约 29 条筛选子集时达到 55.4%（两次运行的均值）。文中还记录了若干部署中实际出过的问题：一条高支持度指南反而有害、合并时静默丢掉出处、被吞掉的 API 错误让全部任务失败却留下看起来合理的日志，以及一个差点把对比做成误导的基线混淆。

局限。 主数字来自 AppWorld，不是作者自己的生产日志；「约 29 条」是筛选子集的规模，不是对所有弱模型通用的剂量。两次运行的均值说明该对照并不宽。开源与产品部署是作者自述，本文未独立核对线上行为。

短评。 评论它把「记忆越多越好」这句口语拆开了：同样的自蒸馏指南，强模型可以吃全集，弱模型多了反而更差。对个人 Agent 来说，这比再提出一种新的记忆格式更紧要——先要按执行模型来决定写回多少条。

是否值得读原文 · 值得。先读中心结论、两组 AppWorld 数字和文末部署教训，约 12 分钟。

第 02 节

RSI（自我迭代 / 人参与的迭代）

周末最重要的不是又一篇「模型改自己」的实验，而是 OpenAI 把预训练损失写成了可以拿来谈节奏和共同上限的公共尺度；同一天的论文里，技能自进化则把失败拆成「指令写错了」还是「模型没遵守」。

OpenAI 首席科学家公开内部对数困惑度，并提议在约 0.68–0.7 窗口到来之前约定行业共同上限

Jakub Pachocki（OpenAI 首席科学家） · OpenAI · 标注 November 22, 2026 · 原文 博文约 12–15 分钟

它说什么。 官方Pachocki 认为，跟踪「更好的压缩器（预测器）」的训练进度，是理解 AI 能力弧线的关键，并主张把困惑度（等价于交叉熵损失）写成实验室之间可比较、并能支撑共同安全标准的指标。他写明：公开内部困惑度会让竞争对手更清楚 OpenAI 的位置，但「建立全行业共享安全措施的紧迫性」压过了这一顾虑。文中报告的是 GPT-3.5 以来主用的内部代码库留出集、固定快照上的对数困惑度：GPT-3.5 约 0.99，对应流畅对话并成为最初 ChatGPT 的基础；GPT-4 约 0.91，已能有效使用思维链，并推动了后来对推理能力的定向激发；当损失降到 0.8 以下，官方称在网络安全和数学上出现了「变革性」能力。这些能力并不是事先就能从精确阈值推出来的，而被写成是这一指标进步带来的涌现。

关于 RSI。 官方他区分两件事：用提示、微调或强化学习去引出已有潜在能力，以及创造出那些难以预测的能力本身。他认为，常被讨论的「完整递归自我改进、不再需要人类监督」这个框架漏掉了更关键的一步：AI 参与预训练算法研究，可能带来台阶式加速。他给出一个类比：他们用开放数学问题评估模型超过一年；当模型升到对数困惑度约 0.76 时，开始连续给出突破性结果。据此他写道，深度学习研究「最早在 2027 年」就有可能出现类似的基础预训练进展井喷。他同时认为，AI 也会显著促进对齐和监控，但「这一进度不太可能快到足以跟上预训练可能达到的全部加速」。外推近期进度，进入约 0.68–0.7 的窗口时，应预期出现新的变革性能力，同时现有的对齐审计会进一步失效、评测与训练意识会进一步增强。因此他提议：前沿实验室应共同约定如何评测和红队这类模型，并基于困惑度和其他测量设立共同上限，在理解与监控能力达到某一具体里程碑（例如思维链监控的后继方案）之前不越过这条线。

局限。 文中自己列了四条挑战：各实验室的评测集和训练数据不同，跨实验室比较并不直接；困惑度不对应某一项人们关心的任务；思维链等预训练之外的进展不会降低该指标，却会大幅提高能力；数据固有熵未知，损失不可能到 0，接近地板时表面上的指标进步会变慢，但更小的损失下降可能对应更大的智力跃迁。这些数字测的是 OpenAI 自己的内部代码库留出集，不能直接当成公开基准上的排名。「2027 年井喷」是作者的外推，原文用的是 conceivably（有可能），不是时间表。不要把公开损失曲线写成已经实现完整 RSI。

短评。 评论它和上周 OpenAI 的研究加速报告、DeepMind 把 RSI 拆成代码、数据和群体三条机制，可以放在一起看：一家在报可核对的内部研发指标，一家在把 RSI 定义写清楚，今天这篇则试图给出一条跨实验室都能盯的尺子，并把最危险的加速点明确写在「预训练算法研究」而不是「模型改自己的权重」上。尺子能不能共用，取决于其他实验室是否愿意用可对照的方式公开自己的损失。

是否值得读原文 · 值得。先读损失阈值、四条挑战和共同上限那段，约 12 分钟。

Perplexity and Intelligence (openai.com)

SkillPlumber：用指令级覆盖率判断失败来自写错还是没遵守；三套执行器上比初始技能高 25.6–30.4 个百分点

Tan、Zhang、Ma 等（MBZUAI / 利物浦大学） · arXiv · 星期五（11-20）新公告 · 原文 摘要与覆盖率消融最有用，约 10 分钟

问题。 论文Agent 技能是写成自然语言的程序性知识，只有指令本身正确、并且被 Agent 遵守时才有用。现有自进化方法往往按整轮结果或出错位置来改技能，分不清失败是指令写错了，还是指令没被遵守。

方法。 论文作者利用指令级覆盖率：把一轮中的每条指令标成 follow、not-follow 或 not covered，从而分开上述两种原因。SkillPlumber 只在覆盖率显示不足的地方改技能：一个持续存在的根因分析 Agent 把每个标签变成修订问题，并对照下一轮检查修订是否成立；一个维护者再把跨任务的调查沉淀进共享策略库。

证据。 论文在三个基准、三套执行器上，SkillPlumber 解开了 64.7%–70.5% 的任务，比初始技能高 25.6–30.4 个百分点，比最强基线高 8.7–14.0 个百分点。去掉覆盖率后，在 SkillsBench、以 GPT-5.5 为执行器时，被挽回的失败减少 20.8%。

局限。 64.7%–70.5% 是三条执行器上的区间，摘要未逐一给出各基准的原始分数。覆盖率标签本身也依赖判定流程，标错会把修订问到错误的位置。这是改技能文本，不是改模型权重。

短评。 评论它给技能自进化加了一条很具体的约束：先分清「写错了」和「没照做」，再决定改哪一句。对在用技能文件、希望 Agent 自己迭代操作说明的人，覆盖率比只看最终成败更可操作。

是否值得读原文 · 关心技能或 harness 自改进的值得读摘要和覆盖率消融，约 10 分钟。

第 03 节

各领域模型能力进展

药物化学里最难的往往不是认出分子，而是在「对靶点更强」和「吸收、代谢更差」之间做取舍。

OpenAI 发布 MedChemBench：99 道题来自 117 篇文献与专利；GPT-6.2 Astra 在 xhigh 档得到 84.5% 的可用分数

OpenAI · 标注 November 20, 2026 · 原文 发布说明约 8–10 分钟

是什么。 官方MedChemBench 评估模型能否把分子结构与实验证据连起来：解释结果、比较化合物、预测性质。基准含 99 道题，来自 117 篇论文与专利，共 761 个不同分子结构。多数题目会提供研究进行到某一时刻时已有的上下文：生物靶点、研究目标、已研究的化合物和部分实验发现。评分分四块：分子结构（原子连接与指定立体化学）、有证据支撑的科学推理、排序与选择、与文献中数值和类别相符的性质预测。

证据。 官方在 xhigh 推理档，GPT-6.2 Astra 得到可用分数的 84.5%，对照为 GPT-6 Astra 83.3%、GPT-6.1 Sol 82.0%、GPT-5.6 Sol 58.2%。官方称 GPT-6 Astra 最强的是重建分子结构和解释实验证据，选择化合物和预测数值性质更难。文中以 PRMT5 抑制剂为例：模型要同时预测细胞水平抑制强度、透过细胞屏障的难易，以及肝酶分解速度；后续实验（对模型隐瞒）显示化合物 23 在细胞中更强，化合物 24 更易透过屏障、在肝酶实验中分解更慢。另一道空间题要求在保留 18 原子环的前提下组装分子：在所有 11 个模型共享的最高推理档（xhigh）上，GPT-6 Astra 十次全部正确，GPT-5.6 Sol 与 GPT-5.6 Luna 十次全部失败。

局限。 这是 OpenAI 自建基准上的官方分数，不是独立评测。GPT-6.2 Astra 相对 GPT-6 Astra 只高 1.2 个百分点，主要拉开的是与 GPT-5.6 系列的差距。题目来自已发表文献，模型是否在预训练中见过相关文本，文中未给出排除说明。不要把 84.5% 写成已经可以替代药物化学家做「下一步测哪个化合物」的决定。

短评。 评论它把「认分子」和「在互相打架的性质之间做预测」拆开了，后一项才是药用价值所在，而官方自己也说这一项更难。适合看题型和评分方式，不必把总分差当成这一代模型的主进展。

是否值得读原文 · 关心科学 Agent 或分子推理的值得读题型说明和 PRMT5 例子，约 8 分钟；只看总分的话，官方这段已经够用。

第 04 节

世界模型 / 具身

交互式世界模型常能「接着往下演」，但训练集里常见的物理规则，会不会压过眼前这段视频给出的证据？

TailWorld：世界模型更容易跟着常见先验走；RIFT 在 2D / 3D 规则迁移上把 ADE 降到 0.0895 / 0.0989

Xiao、Bao、Liu、Chen、Wu（厦门大学 / 东北大学 / 同济大学） · arXiv · 星期五（11-20）新公告 · 原文 摘要、任务定义与表 1 最有用，约 12 分钟

问题。 论文要在新环境里做预测，模型需要先认出当前的物理规则，而只看出相往往不够。作者因此研究视觉校准：用一小段视频里的物体运动和相互作用作为证据，推断当前规则，再从另一个初始状态出发、按该规则预测运动。麻烦在于，不同物理条件的数据量常呈长尾，模型即使看见了支持罕见规则的证据，仍可能偏向常见规则。

方法。 论文他们提出基准 TailWorld：在保持预测初始状态相同的前提下，提供两条参考未来，一条遵循演示规则，一条遵循常见规则，用来测量模型是否偏向常见动力学；训练不平衡和校准信息量被分开控制。方法 RIFT（Rule Inference for Transfer）先学习不同规则如何影响物体运动，再从校准交互中推断当前规则，并把它用到新的初始状态上；它显式控制训练频率对规则推断的影响，使足够信息量的观察能够支持罕见规则。合成实验里，轨迹方法共享冻结的视觉状态读出，以便公平比较。对比还包括未微调的预训练世界模型 Cosmos-Predict2.5-2B 与 Wan2.2-TI2V-5B。

证据。 论文表 1：在 2D 物理规则迁移上，RIFT 的平均位移误差（ADE）为 0.0895、终点位移误差（FDE）为 0.1388；同表里此前较好的 MaNGO 为 ADE 0.1767、FDE 0.3485，Cosmos-Predict2.5-2B 为 ADE 0.4375，Wan2.2-TI2V-5B 为 ADE 0.4693。在 3D 上，RIFT 的 ADE 为 0.0989、FDE 为 0.1205；较好的专用基线 NCF 的 ADE 为 0.1772，GEPS 的 FDE 为 0.3261，Cosmos 与 Wan 的 ADE 分别为 0.5874 和 0.6859。ADE、FDE 的单位是米。真实摆锤视频上也做了评估，但摘要未给出与表 1 同口径的主数字。

局限。 主表是作者自建的合成碰撞场景；Cosmos 与 Wan 未经针对该任务的微调，和专门训练的适应方法不是同一设置。位移误差是轨迹指标，不是「视频看上去像不像」。长尾偏差是核心主张，但跨频率比的详细曲线需要读正文，摘要没有把它写成单一百分数。

短评。 评论它和最近几周「相机一动场景就变形」「模型用自己后半段视频当裁判」是同一类问题的另一面：模型不是看不见证据，而是训练里更常出现的规则，会在预测时把证据压下去。对要靠短演示迁移物理或镜头行为的世界模型，这条比再报一条生成观感更有用。

是否值得读原文 · 关心世界模型或物理一致性的值得读任务定义和表 1，约 12 分钟。

AIGC 视频生成

上一期窗口里已经出现、但未写入的一条：Pika 把「导戏」从提示词做成了边播边改的研究预览。

〔补记 · 11-18〕Pika 发布 Enact 研究预览：可在播放中拖动演员、口头给词并控制相机；官方称暂不对消费者开放

Pika · 标注 November 18, 2026 · 原文 博文与各节技术说明约 12–15 分钟

是什么。 官方Enact 是建立在 Pika H3 Flex 上的实验性直播环境，按亚秒级块生成画面和声音，一边把场景上下文往后带，一边把新的导演指令写进正在生成的内容。官方把它写成接近现场导戏，而不是只在提示框里生成一段成片。

三种交互。 官方Live Staging：用鼠标在正在播放的视频里放置或挪动演员与物体，场景继续播放；官方称在单机服务器上生成速度是播放速度的 1.8 倍，低延迟设置下画面响应（含解码）在 H100 上低于 0.4 秒。Live Actor Direction：用语音或文字给演员说戏，他们会记住备注，并在叫 “Action” 后从第一帧重新拍一条连贯的新镜头；这一模式的画音生成速度是播放速度的 1.75 倍。Live Camera Control：用鼠标在正在播放的场景里控制运镜。演员侧被写成各有性格的 AI Agent，会话内会记住导演备注。官方注明：演员排练示范视频为剪辑后的长度，字幕和导演摄像头画中画是事后加上的。

实现要点。 官方拖动训练需要与光标轨迹严格对齐的前后视频对，真实素材难以提供，因而使用物理驱动的合成数据引擎。为赶上光标，模型被蒸馏到少数采样步，并以短因果块流式解码（标准块 0.7 秒，低延迟 0.17 秒）。运镜方面，官方给出在 8 张 NVIDIA B300、640×480、24 fps 下的数字：首帧 0.51 秒，随后块以 1.50 倍实时速度生成；稳态计算为每 0.708 秒块耗时 0.473 秒，亦即 1.50 倍实时。

局限。 官方这是研究预览，当前不对消费者开放；试用或集成需联系 enterprise@pika.art。运镜基准是 640×480，不是电影级分辨率。1.8 倍、1.75 倍和 1.50 倍是官方在指定硬件上的生成速度，不是质量偏好或镜头一致性分数。示范视频有后期剪辑，不能当成完整连续场次的无剪辑记录。

短评。 评论它把控制从「生成后再改提示」挪到了「播放时直接搬位置、说话、移机位」。对短剧和分镜来说，这条比又一个更长的文生视频模型更接近实际导戏方式，但目前仍是实验室预览，还不是可纳入日常管线的产品。

是否值得读原文 · 做 AI 视频或导戏工作流的值得读三种交互和运镜那节的硬件数字，约 12 分钟；若只关心能否马上用，看文末「暂不对消费者开放」即可。

工具一多，先把全部参数模式塞进上下文，既贵也容易选错。这条同样是上一期窗口里已发布、当时未写入的官方能力。

〔补记 · 11-19〕Gemini API 上线 Tool Retrieval 预览：先只给工具名和描述，需要时再加载完整参数模式

Lucia Loher、Nora Kassner（Gemini API / Google DeepMind） · Google · 标注 November 19, 2026 · 原文 发布说明约 6–8 分钟

是什么。 官方Tool Retrieval 在 Gemini Interactions API 中以预览形式提供。做法是在请求里加入 tool_search，并对希望暂缓加载的工具设置 defer_loading: true。模型仍能看到每个被暂缓工具的名称和描述，但参数模式先不进入上下文；需要某个工具时，模型在同一次请求里按名称索取，API 再加载完整模式并完成函数调用。这三步会出现在 interaction.steps 里，便于检查模型考虑过哪些工具。常用工具可以仍预先加载，长尾工具再暂缓。

配套能力。 官方无需自建或托管索引，搜索在服务端完成。它与前缀缓存兼容：被暂缓的模式不会出现在提示词开头，后来加载的模式加在对话后部，缓存前缀跨轮可保持不变。远程 MCP 服务器也可对整个 mcp_server 设置暂缓加载。若要使用自己的工具注册表、向量索引或按用户权限过滤，可以把 tool_search 设为 "execution": "client"，由应用执行查找，这会为每次搜索增加一次往返，也可以在对话中途暴露新工具。Tool Retrieval 没有单独收费，按所用模型的标准输入、输出价格计费；开启 tool_search 会增加一小块固定输入，随后加载的模式按输入计费。官方称它适用于 Gemini 3.6 及以后的模型，包括所有 Gemini 4 模型。

局限。 这是预览，官方没有在这篇博文里给出选工具准确率或节省了多少 token 的评测数字。省不省 token，取决于「从未加载的模式」是否多于「实际加载的模式」，官方建议按自己的流量测量。不要把一年前 Anthropic 工具搜索文中的 85% 或 49%→74% 挪到这条上。

短评。 评论它要解决的是 Agent 接上几十、上百个工具之后的上下文膨胀，和「先发现、再调用」这个已经出现过的产品方向一致，只是这次是 Gemini API 的官方预览。对要接 MCP 或自建工具目录的人，这篇的配置说明比再看一篇工具选择论文更直接。

是否值得读原文 · 要接 Gemini 工具或 MCP 的值得读设置示例和计价说明，约 6 分钟。

OpenRouter：未发现自身被入侵，但下架三家推理服务商，并从零数据保留名单中移除 125 个端点

OpenRouter · 标注 11/22/2026 · 原文 公告约 5 分钟

是什么。 官方OpenRouter 称，安全研究人员近期报告部分推理服务商出现数据受损，或有证据表明其数据政策未被遵守。官方写明：检测结果没有显示 OpenRouter 自身遭到入侵或未授权访问，但揭示了特定推理服务商的问题。公告感谢 Dragos 的报告。

行动。 官方基于调查结果，OpenRouter 已下架三家服务商；从零数据保留（ZDR）资格中移除 125 个端点，其中既包括研究人员标出的服务商，也包括作为预防措施额外移除的端点；并通知了所有可能受影响的客户。接下来的工作包括：把研究人员的测试方法纳入持续检查、对网络路径做技术核验以发现请求和响应是否被转发到第三方，以及在恢复任何端点的 ZDR 资格前要求相应保证与验证。公告列出已收到的服务商安全说明：Atlas Cloud、Novita（关于 MiniMax 请求的隐私说明）、Phala（11 月初步事故报告）、Together（2026 年 6–7 月请求发生提示词泄漏）。官方同时写明：并非所有受影响服务商都已公开发文，无论是否有公开说明，受影响用户都已收到通知。

局限。 官方没有在公告正文里点名被下架的三家是哪三家，也没有给出受影响客户或请求的数量。服务商说明是当事方自己的通告，细节以各篇为准。ZDR 被移除不等于已经证实发生了泄漏，其中包含预防性下架。

短评。 评论这是路由层而不是模型层的事故：用户以为请求按零数据保留处理，实际还要看后面的推理服务商有没有把提示词转走。对通过聚合接口调用模型的人，这篇的行动清单和「未恢复前先不要默认 ZDR 仍有效」比情绪性的「被黑了」更有用。
