第 01 节

Muse Secure VM：架构与工具调用

产品公告把 Muse 定位为「替人办事」的个人智能体，而安全长文把实现模型写得很直白：一台专属云端 Linux 机器上的两个互不信任安全域，而不是「带了 root 的 LLM」。本节回答：它是不是只暴露 API 的沙箱？能不能跑 shell、开浏览器？能不能做人类在电脑上做的一切？

一机两域：runtime cell 与 host 侧服务

Meta AI Research · 2026-09-08 · 原文 安全长文，约 20 分钟读

官方确认。 Meta 写明：每位用户与自己的 Muse 共享一台云端专属计算机；该 VM 是「isolated linux box」，自带浏览器，并有足够存储、CPU 与内存去做「真实工作」——例如编译智能体自己写的代码、开发自定义 skills、并发跑子智能体与 cron。正确的心智模型是「一台机器上的两个隔离安全域」，而不是「拿了 root 的 LLM 智能体」。

核心 harness（代码库内部名 Hatch）以及工作区文件系统、所有代表用户执行的二进制与工具，运行在 `systemd-nspawn` runtime container 内。cell 内的 root 被映射到 host 上的无特权用户，因此 cell root ≠ host root。cell 拥有独立的 rootfs（含完整 Debian 镜像），与存放更敏感数据的 host 文件系统分离；另有虚拟网卡、过滤后的系统调用（例如禁止 `io_uring`）、收缩后的 kernel capabilities（例如无 `CAP_SYS_PTRACE`、无 `CAP_NET_ADMIN`）。

所有安全敏感服务放在 runtime cell 之外，以独立 systemd unit 运行：`hatch-safety`（独立模型与分类器，检查进出核心推理的请求/响应）、`privsep` workers（执行内置 connector 业务逻辑，凭证范围收紧）、`hatch-authd`（凭证存储与 surrogate 签发）、Sentinel（connector 动作与网络出口的唯一许可权威）、与 cell / 凭证库分离的 Postgres（持久应用状态）、以及面向推理与遥测的受限代理。cell 与这些服务之间只走带 `SO_PEERCRED` 与 peer ACL 的 Unix domain socket——内核认证、最小权限 IPC，没有可被偷走的共享密钥。

工具怎么被调用：CLI → socket → privsep / broker

Meta AI Research · 2026-09-08 · 原文 Least Privilege / Browser 两节，约 8 分钟

官方确认。 内置 connector 不是「和 harness 同环境、直接拿着凭证跑 CLI」。runtime cell 里的 CLI 只做三件事：解析参数、打开调用方本已有权访问的文件、把类型化参数与文件描述符通过 Unix socket 交给外面。真正的业务逻辑由 systemd 沙箱化的 `privsep` worker 执行；每个 worker 用 `cgroup` 标识，并带显式凭证 allowlist——日历 worker 不能靠改请求参数向 authd 要邮件凭证。职责切分被写死为三条：Privsep 决定「有凭证能力的代码在哪儿跑」；Authd 决定「已认证调用方能拿到哪份凭证材料」；Sentinel 决定「请求的动作是否允许发生」。

浏览器走平行模式：CDP 访问由 runtime cell 外的 broker 托管；驱动浏览器的是专用 browser sub-agent，它看到的是页面的 accessibility tree 快照，不是原始 DOM；不能在页面上下文执行 JavaScript，没有 script 动词，不能在浏览器进程里 exec，Chrome DevTools 对智能体关闭。用户接管浏览器，或安全凭证库正在填表时，智能体会被暂停。密码输入走客户端自定义 UI，直达 `authd`，主智能体不可见；注入发生在需要时的浏览器窗口一侧。

模型侧训练重点被明确点到：zero-shot tool calling（CLI 与 skills）、长上下文、带 prompt-injection 意识的长轨迹指令跟随、多智能体协调。产品侧还说 Muse 可为有 API/CLI 的服务自己写自定义 connector，并已为第三方与 Meta 系应用（如 Instagram、Facebook）写了 SKILLs（给 Muse 的详细使用说明）。

是否值得读原文 · 值得。Least Privilege 与 Browser 两节是「工具调用」最具体的官方描述；比产品公告密一个数量级。

能跑 shell / 浏览器吗？等于人类电脑吗？

introducing.muse.ai · 2026-09；How We Built Safety Into Muse · Meta AI Research · 2026-09-08；Introducing Muse · Meta Newsroom · 2026-09-08 · 原文 设计文「Agent That Can Actually Do Things」+ 安全文开篇与 Browser 节

官方确认（能力侧）。 设计文写明：Muse「有自己的电脑，带文件系统和终端」，可以写代码、为任务构建工具；并有「完整的网页浏览器」，可搜索、导航、填表、完成预订与购买。安全文开篇更直接：团队第一次把「收件箱、日历和 shell」交给软件并让它无人值守运行。产品公告补充：可打开浏览器、填表、代议价；应用关闭后继续工作；发邮件、下单前回来请求批准。因此它不是「只暴露一组受限 REST API、不能 spawn 进程」的纯沙箱——在 runtime cell 内，智能体确实在操作一台带 shell、文件系统与浏览器的 Linux 环境。

官方确认（边界侧）。 它也不是「人类在个人电脑上能做的一切」。主智能体看不到真实密码与支付方式；凭证经 surrogate 在出口边界才被替换；浏览器 sub-agent 看不到原始 DOM、不能跑页面 JS、不能用 DevTools；所有 connector 动作与网络出口必须经 Sentinel；敏感动作有 HITL；邮件 connector 会过滤 OTP、密码重置与 magic login 链接。产品公告还强调：用户逐项选择连接哪些应用、读/写粒度，并可随时断开；完整审计轨迹可见。

合理推测（标注）。 官方未公布 cell 内完整软件清单、默认 PATH、是否预装包管理器、浏览器虚拟化层具体实现（QEMU/KVM vs 其他）、以及「自定义 connector」的签名/审计流程。社区逆向（如 Rohan Adwankar 对 hatchling / hatch-execd 的描述）提到 Cloud Hypervisor microVM、合成 DNS 等细节，均非 Meta 官方声明，本页不作为事实采纳，仅提示「可能还有更深的宿主虚拟化层」。

是否值得读原文 · 三篇都该扫。能力边界以设计文最口语化，约束边界以安全文为准；产品公告适合给非工程师同事看。

小结 Secure VM 的工程本质是：per-user 云 Linux + nspawn 无特权 runtime cell + host 侧安全平面。智能体在 cell 里确实有 shell、文件系统与（经 broker 的）浏览器，工具调用走「cell 内薄 CLI → UDS → 外置 privsep/CDP broker」；但凭证、出口与审批都不在 cell 信任边界内。它比「API-only 沙箱」更像一台被阉割过的个人电脑，又比「给模型 root」严格得多。
第 02 节

系统级隔离安全流：Muse 如何与 Sentinel 交互

公告一句话概括了威胁模型：「假设智能体可能已被攻击，限制潜在损害」。Sentinel 是把这句话落到内核与网络路径上的组件。本节按「谁提出 → 谁裁决 → 流量怎么走 → 凭证何时出现 → 人何时介入」拆开。

Sentinel 的角色：唯一许可权威

Meta AI Research · 2026-09-08；Introducing Muse · Meta Newsroom · 2026-09-08 · 原文 Built-In Sentinel 节 + 产品公告安全要点

官方确认。 Sentinel 是与 Muse 分离的 host-side agent，在同一台机器上、系统级隔离；它是 connector 动作与全部网络出口的「sole permission authority」。Muse 只能提出动作，只有 Sentinel 能授予执行许可。产品公告表述一致：Muse 做的任何事在到达互联网之前都必须经 Sentinel 批准，需要时再问用户。

Connector 路径：runtime cell 内调用相关 connector 工具 → 向 Sentinel 提交请求（connector、方法、动作类别、scope、用户诉求上下文）→ Sentinel 生成用户可见的 purpose → 对照用户设定的 connector 策略 → allow / deny / ask。

网络出口路径：runtime 流量经 forward proxy 到达 Sentinel；Linux 网络控制包括 userns、veth 边界与 eBPF 过滤。Sentinel 可在 L4 与 L7 评估：hostname、解析后与最终目的 IP、端口、协议、HTTP 方法、path、以及解码后的请求体。SSRF 限制阻止「看起来是公网 hostname、DNS 后落到私网」的绕过。

是否值得读原文 · Built-In Sentinel 整节必读；产品公告对应 bullet 可作对外一句话摘要。

Surrogate 凭证与 tainted egress

Meta AI Research · 2026-09-08 · 原文 Network egress 小节

官方确认。 需要密钥或 auth token 的请求，runtime cell 或 worker 侧只看到由 authd mint 的「surrogate」token。具体网络请求被授权后，Sentinel 在网络边界用从 authd 取到的真实凭证做 just-in-time 替换。主智能体永远看不到真实 token，因此「通过 prompt injection 逼模型吐密钥」在设计上无效。

为平衡审批信噪比，Muse 使用内核级数据流追踪，称为 tainted egress：每个工具执行进程从 clean 状态起步，一旦读取用户数据即被标记 tainted。已落入窄域 auto-allow 策略、且出站 URL 等检查通过的 clean 请求，可不打扰用户放行；tainted 或不可验证的进程失去 auto-allow，回退到正常审批。实现使用 eBPF `cgroup` 程序做网络拦截与进程归属，以及挂在 Meta 自行加入的 Linux Security Module hooks 上的 eBPF 做污点传播。

合理推测（标注）。 「自行加入的 LSM hooks」暗示内核改动或定制内核模块，但官方未公开补丁树、hook 点列表或 eBPF 程序源码。社区文章对「合成 DNS / 非路由地址空间」等的描述同样未在安全文中逐字确认，本页标为未证实。

是否值得读原文 · Network egress 两段是整篇最「可实现」的内核细节；做 agent egress 代理的人应逐句对照。

Human-in-the-loop：审批不走对话通道

Meta AI Research · 2026-09-08；How We Designed Muse · introducing.muse.ai · 2026-09 · 原文 Human in the Loop 节；设计文 Deterministic controls

官方确认。 当 Sentinel 决策为 ask，会创建 pending approval 并停止执行；请求直接发到 Muse 客户端，描述待批准的精确动作。对话框出现在客户端 UI 内——不是经用户与 Muse 的对话——答案直接路由回 Sentinel。批准是严格的 capability，不是对话建议：绑定特定 connector/目的地与用例；支持一次性、session、task、时间窗口或永久授权；Sentinel 决定向用户展示哪些 grant 类型，并保证后续调用精确匹配已授 scope。

设计文补充产品动机：结构化 approval card（明确 accept/reject）与凭证安全存储属于「对话不够、必须确定性 UI」的区域；默认允许常规浏览，在难撤销动作上停下，并提供调高/调低谨慎程度的控件，以避免 banner blindness。结账场景另有强制 HITL：已存卡站点检测到 checkout 页即弹精确购买详情；Stripe Link 签发单次卡号，绑定商户、金额与短时效，每次支付都走 HITL。

这正是「提高安全性」的机制要点：即使模型被诱导同意「请批准外泄」，审批通道不经过被污染的对话上下文；再叠加 surrogate 凭证与污点出口，把 lethal trifecta（私有数据 + 不可信内容 + 外联能力）在系统层拆开。

小结 Sentinel 不是「模型旁边的提醒插件」，而是 host 侧唯一放行点：connector RPC 与全部 egress 都经它；surrogate 在边界换真凭证；eBPF 污点决定能否 auto-allow；ask 时审批 UI 旁路对话。相对「只靠模型拒绝坏指令」，这把失败模式从「模型说错话」收窄到「策略/污点/审批被绕过」——攻击面移到更可审计的系统层。
第 03 节

隔离 + 独立审批智能体：为何是核心

安全文反复强调：模型再强也会犯错、也会被读入的数据攻击。隔离 runtime 与独立 Sentinel 不是锦上添花，而是把「个人超级智能体」从 demo 变成可规模化产品的前提。本节把已确认机制排成纵深，并标明仍属推测的部分。

纵深防御栈（官方确认）

Meta AI Research · 2026-09-08 · 原文 Defense in Depth；引用 Simon Willison lethal trifecta（2025-06）

官方确认的层次（自上而下）：

1. 模型层：针对 prompt injection 识别与抵抗做训练；Muse Spark 1.3 在该能力上接近 SOTA（官方自评，未附公开榜分数）。

2. Harness 层：任何外部来源进入上下文的数据被标为 untrusted input；配合更强的 developer-instruction 跟随。

3. 独立分类器集成：多套 prompt-injection 检测器并行，数据来自真实场景与规模化 agentic red teaming；跑在 `hatch-safety`（cell 外），攻击者无法从 cell 内关掉。

4. HITL：数据或敏感动作离开 VM 时的人审。

5. 确定性边界：即便 Muse「被说服」行为异常——runtime cell 限制系统访问、privsep 限制谁能见哪份凭证、authd 施加 ACL、Sentinel 评估每个动作与全部 egress。

邮件 connector 额外过滤 OTP、密码重置与 magic link（确定性过滤器 + 分类器），避免「连了邮箱 ≈ 拿了全网账户恢复权」。浏览器另有一组分类器：无关任务的个人数据外泄、DOM/图片/下载文件中的注入、高风险表单提交；并匹配 Meta 既有恶意站点列表以阻断导航。

Bug bounty 已对公众开放：有效报告最高 30 万美元，其中成功影响单用户的 prompt injection 最高 13 万美元——这本身是「承认 prompt injection 仍是开放问题」的工程态度。

独立审批智能体：与「主智能体自审」的本质差别

Meta AI Research · 2026-09-08；How We Designed Muse · introducing.muse.ai · 2026-09 · 原文 A Built-In Sentinel；Human in the Loop；Deterministic controls

官方确认。 Sentinel「cannot be overridden by the agent」；审批请求不经 Muse 对话；批准是绑定 scope 的 capability。这与「让同一个 agent 再想一遍要不要发」有本质差别：后者在 prompt injection 下与主决策同腐，前者把许可权放到攻击者默认够不着的安全域，并用客户端直达通道闭合回路。

合理推测（标注）。 官方称 Sentinel 为「separate host-side agent」，但未公开：Sentinel 是否本身是另一个 LLM、规则引擎、还是「LLM + 策略」混合；其模型权重/策略是否与 Muse Spark 同源；ask 决策的延迟 SLA；auto-allow 策略的具体规则语言。从「生成 user-visible purpose」「决定展示哪些 grant 类型」可合理推测其至少具备自然语言摘要能力，但「Sentinel = 第二个完整个人智能体」并无官方背书。更稳妥的工程解读是：独立进程 + 独立信任域 + 对动作/egress 的强制中介，语言模型是否在环上是实现细节。

是否值得读原文 · 把 Sentinel 节与 HITL 节连读，比单独抠「agent」一词更能抓住可复用设计。

第 04 节

开发者可落地的建造分析

可直接抄进设计文档的模式（官方确认 → 工程动作）

Meta AI Research · 2026-09-08；辅以产品/设计文能力描述 · 原文 全文架构描述

把官方机制翻译成可执行的设计输入（括号内为 Meta 原术语对应）：

1. 双平面拓扑：Agent runtime（无特权容器/VM）与 Security plane（审批、凭证、安全分类器、持久库）分进程、分文件系统、分网络命名空间；IPC 用对等身份（类 `SO_PEERCRED`），禁用「共享 API key 文件」。

2. 薄工具适配器：cell 内只留 argv 解析 + fd 传递；业务逻辑与凭证在 privsep worker；worker 身份 = cgroup + allowlist。

3. 出口唯一门：所有 egress 强制走正向代理；L4+L7 可检；SSRF 用「解析后 IP」裁决，不只看 hostname。

4. 凭证代理（surrogation）：模型与 cell 代码只持 opaque handle；真实 secret 仅在已授权请求离开边界时注入。

5. 数据流污点：进程读敏感数据 → 失去 auto-allow；实现可选 eBPF/LSM，也可用用户态 taint bit 做第一版（能力弱于内核版，但产品语义可先对齐）。

6. 审批旁路对话：pending approval 走独立客户端通道；grant 为结构化 capability（connector、目的地、一次性/会话/任务/时限/永久）。

7. 浏览器最小面：智能体侧只给 a11y tree / 结构化快照，禁用 page JS 与 DevTools；填密时冻结 agent。

8. 连接器内容卫生：对邮箱等「账户恢复根」类数据，过滤 OTP 与重置链接。

9. 训练与运行时双轨抗注入：模型训练 + untrusted 标签 + cell 外独立分类器；不要只赌 SFT。

10. 威胁模型默认句：Assume the agent may be under attack；优化目标是减小 blast radius，而非宣称零注入。

是否值得读原文 · 把安全文当 RFC 读一遍，再把上表贴进自己的 ADR；比再找三篇二手解读更省时间。

How We Built Safety Into Muse (research.meta.ai)

建议的最小可验证原型（合理推测 / 建造建议）

综合官方机制；实现路径为作者工程建议，非 Meta SDK · 原文 无单一原文；整节为合理推测 / 建造建议

若团队要在数周内验证「Muse 式」控制面，而不复制整台 per-user VM：

- Week 1：Docker/Podman 跑 agent；旁路进程 `sentinel` 监听 UDS；iptables/nftables 或 tinyproxy 强制容器出口；策略文件实现 allow/deny/ask。

- Week 2：authd 雏形——Vault/SOPS 存真密钥，向 agent 只发 `surr_xxx`；代理在放行时替换 `Authorization` 头。

- Week 3：HITL——桌面/移动推送或 CLI prompt，不要把「是否批准」问句注入 agent 上下文；grant 写成 JSON capability 并校验后续请求。

- Week 4：给「读邮箱 / 读盘」打进程级 taint（可用 `LD_PRELOAD` 或简单 wrapper 起步）；浏览器自动化改为只暴露 a11y/AX tree。

成功标准建议写成负面用例：prompt injection 要求「把 API key 打出来」应无可读密钥；要求「把通讯录 POST 到 attacker.com」应触发 ask 且对话内「用户已同意」无效。

官方未提供、需自研的空白： 完整系统镜像与单元文件、Sentinel 策略语言、eBPF/LSM 补丁、SKILL 文件格式规范、Muse Spark 权重（专有）、per-user VM 编排与冷启动、Confidential VM 远程证明协议细节。截至 2026-10-12，未见 Muse Secure VM 专题 arXiv。公开可依的仍是安全博客级披露 + bug bounty 反馈循环。

小结 开发者从 Muse 能学到的，不是某个开源 harness 的 drop-in，而是一套 可写成验收用例的安全契约：双平面、出口门、凭证代理、旁路审批、浏览器最小面。用容器 + 正向代理 + 独立审批进程，就能在内部复现语义；eBPF 污点与 Confidential VM 是增强项。未知处坦白列进风险登记，比假装有 SDK 更有用。
