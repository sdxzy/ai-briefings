第 01 节

一句话读懂

先把结论放在前面

一句话

Git 假设每个客户端都可能离线、所以人手一份完整仓库；Anthropic 的客户端几乎全是一直在线的智能体和 CI 任务，于是他们把仓库「收回」服务端，客户端只按需取文件，提交、变基、合并、blame 全在服务端做。

  1. 问题是规模。每天合入的改动从 5 月约 2,500 次涨到 9 月超过 30,000 次；主分支历史近 100 GB，CI 每天约 2,500 万次检出，按 Git 方式硬拉要 600 PB/天。
  2. Git 的补丁打不住了。浅克隆、稀疏检出、几百台内部镜像、存在 blob 存储里的仓库快照都用过，越用越难运维。
  3. Scion 的解法是「服务端算、客户端少拿」。改动存成只记差异的 changeset；历史、blame 靠派生数据在服务端回答；文件经「节点 daemon → 区域 cache → server」三层缓存按需流下来。
  4. 效果。基础设施的 CPU/内存比原 Git 镜像集群小 200 倍，CI 省下 25% CPU 容量，智能体每个改动在版本控制上花的时间从 34 分钟降到 3.7 分钟。
  5. 代价。不能离线、要重建评审/搜索/CI 全套；放弃全局锁合并队列，接受并发改动偶尔冲突，再在合入后修。

Anthropic 自己说：Scion 不适合当通用的 Git 替代品。值得带走的是思路——把服务端做成能回答问题的服务，别让每个客户端都背整个仓库。

后面的顺序：第 2 节补 Git 背景，第 3 节逐个看问题，第 4 节看 Scion 怎么解、配图和一个从头到尾的例子，第 5 节对照表，第 6 节和 Piper / Sapling 比，第 7–9 节是建议、未知和术语。

第 02 节

背景：Git 怎么工作，规模大了为什么会坏

只讲读懂后文所需的部分。

提交、树和对象

Git 的仓库是一堆按内容哈希寻址的对象：blob 存文件内容，tree 存目录（文件名指向 blob 或子 tree），commit 指向一棵根 tree、指向父提交，再加作者和说明行业做法。所以 Git 的提交本质是「整个仓库此刻的快照」，靠哈希共享没变的部分。

记住这一点：Scion 改的正是这里。它的 changeset 不指向整棵树，只记录「相对第一个父提交改了哪些文件」官方。

克隆、拉取和 packfile

git clone 把全部历史搬到本地，之后看 diff、看历史、blame、切到任意版本都能离线完成官方。拉取时，客户端和服务端先「协商」：客户端说「我已经有这些提交」，服务端算出它缺什么，压成一个 packfile（对象的压缩包，内部常用增量压缩）发回去行业做法。

这套设计对绝大多数仓库都是对的，也是 Git 成为标准的原因——Anthropic 原文也这么说官方。问题在于，服务端每接一个客户端都要算一次「你缺什么」，再现场打包。

monorepo、合并与变基

monorepo 指整个公司的代码放在一个仓库里，Anthropic 就是这样官方。好处是改接口的人能在同一个提交里改完所有调用方。坏处是仓库随时间只增不减。

两条分支汇合有两种做法：merge 生成一个有两个父提交的合并提交；rebase 把你的提交「挪」到对方最新提交之后重放一遍，历史变成一条直线行业做法。在 trunk-based（主干开发）流程里，大家都往 main 合，很少长期分支。

合并队列（merge queue）

主干上合入的人一多，就会出现「我测的时候 main 是 A，合进去时 main 已经是 C」的问题。合并队列的做法是排队：每个改动都要跟「最新 main + 排在前面的改动」放在一起测，测过才合，保证 main 永远是绿的行业做法。GitHub 的合并队列就是按先进先出、在临时分支上把前面的 PR 叠在一起测行业做法。

本质上这是一种「全局锁」：同一时刻只有一条被确认的 main，大家按顺序过关。Anthropic 原文用的词就是 global repository lock官方。

Git 自带的「瘦身」手段

仓库太大时，Git 有几种只拿一部分的办法官方行业做法：

  • 浅克隆（shallow clone）：只拿最近几层历史；
  • 稀疏检出（sparse checkout）：只把部分目录放到磁盘上；
  • promisor remote / 部分克隆：先不拿 blob，用到再向远端要。

再往外一层是大公司常用的变通：自建 Git 镜像分担流量，把仓库快照（seed，种子）放在 blob 存储里，新机器先解压快照再增量拉官方。Anthropic 这些都用过官方。

为什么规模一大就坏

把上面串起来：Git 的每个副本都是完整仓库、每次拉取都要服务端现算、每个改动都要排队过全局锁。人类规模下，这三件事都不贵。当客户端变成成千上万个同时在线的智能体，三件事一起变贵。下一节逐个看。

第 03 节

他们遇到的问题

数字全部来自原文和原文图表；场景是为了把数字变直观而构造的。

问题 0：合入量十倍增长，而且看不到头

5 月平均每天合入约 2,500 次，9 月超过 30,000 次官方。原文图上的峰值是 9 月 9 日的 30,401 次官方；同一张图的 7 日均线在 9 月上旬大约一万五到一万八〔推测：读图估计〕。所以「每天 3 万次」更准确的读法是：9 月已经出现超过 3 万次的日子，平均还没到。

Anthropic 认为对合入代码的潜在需求「几乎是无限的」，每拆掉一个瓶颈，产出的代码量就立刻再涨官方。图上还能看到 6–7 月 GitHub PR（蓝色）被 Antique change request（橙色）几乎完全取代官方：读图，这大致就是迁移窗口推测。

问题 1：每个副本都是完整仓库 → 流量爆炸

主分支历史近 100 GB，压缩后的工作区超过 25 GB；CI 每天约 2,500 万次检出，这还没算开发环境、智能体沙箱和研究任务；全部按 Git 方式硬拉，每天超过 600 PB官方。

推测这个 600 PB 基本就是 2,500 万 × 约 25 GB 的乘积（约 625 PB），即「每次检出都拿一份完整压缩工作区」。

示意早上 9 点，2,000 个智能体沙箱同时接到任务，每个都要一份 25 GB 的工作区：一次就是 50 TB。而每个智能体可能只改 services/billing/ 下的三个文件。

问题 2：镜像和种子越来越难养

为扛住负载，他们最多时运维了几百台内部 Git 镜像官方。镜像一旦装不下仓库（磁盘或内存到顶），就不再能扩官方。

种子的问题更隐蔽：两次刷新之间，种子离 main 最新提交越来越远官方。示意按每天 2 万次合入算，每小时约 830 个提交；种子 6 小时刷新一次，最坏时新机器解完种子还要追 5,000 个提交，追的时候 main 又往前跑了。

问题 3：部分克隆上，依赖历史的操作很难做对

diff、blame 这类要看历史的操作，在部分克隆上越来越需要小心伺候才能正常工作官方。

更普遍的问题是：一个 CI 任务或工具只想问一句「这一行最后是谁改的」「这两个提交什么关系」，在 Git 下要么自己维护一份本地仓库，要么指望托管平台恰好有对应的 API官方。示意一个自动 revert 机器人要找出「哪个提交让测试变红」，得先克隆、再 bisect，光准备仓库就要几分钟。

问题 4：服务端为每个客户端现算、现打包

Git 的协商要服务端算出客户端缺什么，再做增量压缩，响应是一个可能几 GB 的 packfile〔官方：原文对比 Scion 时描述〕。断了就得重来，结果也很难被别的客户端复用推测。

问题 5：提交成本和全局状态

在 Git 里，你本地提交再 push。服务端接收 push 时要接 packfile、移动 ref。Anthropic 的要求是：提交的成本要跟改动大小成正比，而不是跟仓库大小成正比，否则服务端跟不上官方。所有服务器都要达成一致的全局状态（比如大量分支 ref）被他们视为「迫在眉睫的扩展问题」官方。

问题 6：合并队列的全局锁扛不住

原文的问题很直接：测试还在跑的时候，几百甚至几千个改动可能已经合进去了，那 CI 还意味着什么官方？他们没能有效复制业界标准的「合并队列上的全局仓库锁」官方。

示意假设一轮完整测试 20 分钟，每天 3 万次合入平均每分钟约 21 次。严格排队时，一轮测试期间就有约 400 个改动在后面等；任何一个失败，后面的组合都要重测。

问题 7：智能体会走「不该存在的捷径」

这不是 Git 的问题，而是迁移中人的问题。智能体有时会为了迎合某种本不该被允许的模式而违反系统的核心约束官方。原文的例子：好几个系统想知道「某个改动何时合进 main」，做法是线性读完整个提交日志，而不是去问代码评审工具官方。

另一个例子是对抗式评审（adversarial review）有时目光短浅：一次评审对「信任另一个内部服务」过度防御，让 Claude 加了一堆多余的校验和复杂度官方。

问题 8：大 monorepo 里的权限

代码全在一个仓库里，最敏感的代码怎么保护？这和规模问题一样重要官方。

第 04 节

Scion 的设计：每一块解决哪个问题

先看总图，再逐块拆，最后跟一个智能体的改动走一遍。

架构总图

原则一：客户端一直在线，客户端与服务端不对称 → 解决问题 1、3

Scion 默认服务端永远可达，客户端需要什么再取什么官方。服务端负责回答历史和 blame、创建提交、做合并和变基；客户端只维护有上限的本地对象缓存、把工作区文件摆到磁盘上、监视文件变化官方。

客户端自己几乎算不了什么，换来的是本地要的数据少得多官方。这是整套设计的根：Git 里「每个客户端都能当完整服务器」，Scion 明确不要官方。

原则二：版本控制是一个服务，查询全部开放成 API → 解决问题 3

客户端用到的所有查询，同样以 API 开放，所以很多任务根本不需要本地仓库官方。原文点名：自动 bisect 和自动 revert 流水线，没有这种便宜的程序化访问，在这个规模下就不现实官方。

迁移早期，Scion 甚至只回答这类「元数据」查询，还没有自己的客户端和协议官方。推测这说明先做服务端 API 就能先解掉一部分负载，是一条可以分步走的路线。

原则三：工作区可有可无，稀疏是默认 → 解决问题 1

能不检出就不检出。比如 CI 要看某个提交和它的 merge base 之间的 diff，直接问服务端官方。很多写操作也能完全走 API，不需要检出官方。

真要文件落盘时，协议以两种方式为中心官方：稀疏检出只拿客户端要的目录；虚拟化检出在读到文件时才实际生成，所以只为真正读过的东西付费。

数据结构：changeset 与派生数据 → 解决问题 5、3

Scion 的工作单位叫 changeset，是一条预写日志（write-ahead log）里的记录官方。它和 Git 提交差不多，区别是：不指向整棵树，而是列出相对第一个父提交改了哪些文件，并带上指向 blob 存储里压缩内容的哈希指针官方。changeset 在服务端创建，立刻各处可见官方。

原文的示例图里，一个 changeset 的作者是 Claude，file_changes 列了三行：改了 docs/guide.md、删了 src/legacy.rs、改了可执行的 tools/build.sh；根 tree 和子 tree 由服务端派生，不存在 changeset 里官方：原文图。

为什么快：没有 packfile 要接，没有加锁和跨服务器协调，也没有 ref 要移动官方。Scion 技术上支持 ref，但创建和拉取提交都不涉及 ref；移动 ref 是对 Spanner 单行的一次 compare-and-swap，跟创建 changeset 分开发生官方。开发流程也刻意少用 ref，只保留 main 和发布分支官方。

只记差异就答不了「这行最后谁改的」。所以 Scion 从 changeset 构建 派生数据：blame 专用结构、路径历史、提交图的跳表等官方。每种派生数据都递归定义：一个 changeset 的值由它父提交的值算出来官方。

这个通用机制有三个好处官方：新加一种索引很容易（他们后来加过拷贝检测、按路径搜文件的索引）；每种可以选立刻算还是延后算；客户端看不到内部结构，所以优化不用改客户端。

推测递归定义的意义在于：新 changeset 的派生数据只依赖父提交的结果加上本次改动，成本跟改动大小走，正好满足「提交成本与改动成正比」。原文没有明说这层因果，但两者是对得上的。

脚注里还有一个小选择：合并提交只记录相对第一个父提交的改动，因为在 trunk-based 的 monorepo 里，大家只关心主线上的历史和 blame官方。

横向扩展：内容寻址 + 无状态服务器 → 解决问题 2、4

所有数据都按内容寻址，存进去就不再改变，所以任何服务器都可以缓存它，不用跟别人确认官方。scion-server 因此基本是「会算派生数据的大缓存」，算完写回 Spanner官方。整个系统里没有任何地方存着一份完整展开的仓库，连服务端也没有；没有 packfile，也就不需要仓库维护官方。

推测这直接对应问题 2：镜像要的是「完整、最新的一份副本」，而 Scion 的每个缓存只需要持有「被问过的、永不改变的对象」，不存在「落后于 main」这个概念。

拉取协议：只说「我要什么」 → 解决问题 4

Scion 的协商不告诉服务端客户端已经有什么，只针对客户端想要的 tree 和 blob官方。从根 tree 开始，客户端查本地缺哪些 tree，递归地要，再对 blob 重复一遍官方。

每个请求都是一个永不改变的具体对象，所以任何一层缓存都能回答，架构就像传统的分级缓存；没有单个几 GB 的 packfile，所以高效、可断点续传官方。稀疏和虚拟检出也不用特殊支持：不想要的 tree 不去要就行官方。

三层缓存：daemon → cache → server → 解决问题 1、2、4

在集群里，scn 客户端通过 socket 连本机的 scion-daemon，由它为整台节点存对象；同一节点上的任务大多复用同一批对象官方。daemon 从一个定期刷新的快照起步，之后只跟本区域的 scion-cache 说话官方。

scion-cache 直接从内存里、按 daemon 要用的磁盘格式流式发对象，不用替客户端算缺什么、也不用做增量压缩官方。cache 未命中，才去问权威的 scion-server，后者按需读 Spanner 或云存储官方。

三层响应同一套 RPC，客户端不用知道缓存拓扑；理论上任何一层都能直连任何一层，但他们严格强制逐层访问，避免一个区域 cache 故障时把上游 server 冲垮官方。每层缓存命中率都超过 99%，且不需要长期状态，扩容容易官方。

推测注意快照在这里的角色变了：Git 时代种子落后 main 是硬伤；在 Scion 里，快照只是让新节点的本地缓存别从零开始，缺的对象照样按需取，落后多少都不影响正确性。

合入流程：放弃全局锁，改成合入后、部署前测试 → 解决问题 6

他们投入的是合入后（post-merge）和部署前（pre-deploy）的自动化测试官方。代价原文也写了：并发的改动可能互相冲突，但 Claude 通常修冲突比人类发现冲突还快官方。

推测这套能成立，靠的是前面的服务端 API：自动 bisect 和 revert 流水线要能便宜地查提交关系和 blame，问题 3 解掉了，问题 6 才有退路。

人和权限 → 解决问题 7、8

对问题 7，原文的答案是人：工程师的工作很多时候是对 Claude 说「不」官方。团队成员仍然评审每一个改动，但看的是改动的意图，而不是逐行读代码官方。

对问题 8：Scion 支持仓库级的细粒度访问控制，也能对单个目录设权限，保护最敏感的代码又不丢 monorepo 的好处官方。他们的评审工具能表达复杂的语义审批约束，比如把只改注释和改敏感逻辑区分开，让人类评审者专注于影响最大的改动官方。

运维上，他们用 Claude Tag 在 Slack 里给每个组件配一个专门盯健康的 Claude，叫「superfan」：scion-daemon、scion-cache、Antique 合并队列各有一个，能看遥测和日志官方。传统告警照样有，但 superfan 能发现细微和新型的问题官方。

走一遍：一个智能体的改动怎样从检出到合入

下面这个例子是构造的示意，每一步标注了依据。

  1. 接任务、检出。一个 Claude 在 CI 节点的沙箱里接到任务：给 services/billing/ 的重试逻辑加上限。它只要这个目录，所以发起稀疏检出；客户端从根 tree 开始，向本机 daemon 要缺的 tree，再要 blob。daemon 从快照起步，大部分对象本机已有，缺的问区域 cache官方：机制。原文实测，智能体环境新建工作区的中位数从 Git 的 7.1 分钟降到 5.1 秒官方。
  2. 改代码。它改了 3 个文件。客户端一直在监视文件变化，所以 status 不用扫整个工作区官方：机制；智能体环境 status 从 4.3 秒降到 0.2 秒以内官方。
  3. 提交。提交在服务端创建，生成一个 changeset：作者、说明、父提交，加三行 file_changes 和对应 blob 的哈希官方：机制。没有 push 这一步。智能体环境提交从 18 秒降到 761 毫秒官方。推测新文件内容怎么上传到 blob 存储，原文没写。
  4. 评审。改动成为 Antique 里的一个 change request。语义审批规则判断这是逻辑改动而非只改注释，要求对应的人类审批官方：机制；人看的是意图，不逐行读官方。
  5. 落地。审批通过后，服务端把它变基到最新的 main 上，然后推进 main ref。推测原文只说变基、合并在服务端做，移动 ref 是 Spanner 单行 CAS；「先 rebase 再 CAS、CAS 失败就重试」是根据这两点拼出来的，Antique 的落地细节原文没讲。
  6. 派生数据。新 changeset 的 blame、路径历史由父提交的结果递归算出，可以立刻算，也可以等有人问时再算官方：机制。
  7. 合入后测试。合入后、部署前的自动化测试开始跑；这期间可能已经又合进去几百个改动。示意如果测试变红，自动 bisect 流水线通过 API 查提交关系，找出肇事改动，revert 流水线回滚它；如果只是和另一个改动冲突，再派一个 Claude 去修〔官方：这些流水线存在，具体判定逻辑为示意〕。

把全程加起来：智能体环境里，每个 change request 花在版本控制上的总时间中位数从 34 分钟降到 3.7 分钟（×9.2）；图上同一行标注「约 11,000 agent hours a day」官方：图表。推测这应该是指每天省下的智能体时长，图上没写清楚。

整体效果

  • 基础设施的 CPU 和内存需求比原来的 Git 镜像集群小 200 倍官方；
  • CI 和研究任务检出快两个数量级，从几分钟到几秒；仅 CI 就省下 25% 的 CPU 容量官方；
  • 开发机：拉最新 87 秒 → 3.5 秒，检出 15 秒 → 1.1 秒，变基 13 秒 → 2.7 秒，status 3.9 秒 → 19 毫秒，diff 407 → 67 毫秒；提交 1.4 → 1.1 秒，几乎没变〔官方：图表，中位数〕；
  • 计算任务开始时的检出 175 → 22 秒（×8.0，图注约 85,000 机器小时/天）；CI 任务里的检出 31 → 3.5 秒（×8.8，图注约 195,000 机器小时/天）官方：图表。

推测正文说 CI 检出快「两个数量级」，但图上 CI 检出是 ×8.8，两者对不上，可能统计口径不同（比如正文对比的是早期 Git 方案，或包含了排队）。原文没解释。

建造速度：7 个人在 5 个月里做出 Scion、Antique 和半打相关系统并完成迁移，期间日合入量涨了 10 倍官方。Scion 和 Antique 代码目录自 1 月以来合入了 12,257 次改动官方：图表。一个早期例子：手写的 Git → Scion 导入流水线原型，交给内部早期版本的 Claude Mythos Preview 重写，内存降到 1/20，速度快 4 倍，导入顺序和数据结构的隐含约束都保留了官方。

第 06 节

跟 Git、Piper、Sapling 有什么不同

原文只说 Scion 借鉴了 Google Piper 和 Meta Sapling「来之不易的经验」，没有逐条比较官方。下面的对比用的是各自的公开资料，比较本身是本页的归纳推测。

和 Git 比

  • 离线 vs 在线：Git 每个克隆都完整、可离线；Scion 假设一直在线官方。
  • 快照 vs 差异：Git 提交指向整棵树；changeset 只列改动文件，树由服务端派生官方。
  • 客户端算 vs 服务端算：Git 客户端能做一切；Scion 客户端几乎只负责摆文件官方。
  • 协商：Git 拉取要告诉服务端「我有什么」；Scion 只说「我要什么」官方。
  • 兼容性：原文没有说 Scion 兼容 Git 协议或命令；它强调 Scion「与 Git 差异很大」官方。

和 Google Piper 比

Piper 是 Google 内部的集中式版本控制，底层先用 Bigtable 后用 Spanner，跨 10 个数据中心用 Paxos 复制行业做法。日常用 CitC（Clients in the Cloud）：云端后端加本地 FUSE 文件系统，让人觉得面前是完整仓库，本地副本平均不到 10 个文件；多数开发者做主干开发，分支主要用于发布行业做法。

2016 年的数字是：86 TB、20 亿行代码，25,000 名开发者每天 16,000 次改动，外加 24,000 次机器人提交行业做法。

推测Scion 和 Piper 思路很近：集中式、在线、Spanner、按需物化、主干开发、少分支。从公开资料看，Scion 的特点在于：客户端是智能体和 CI 任务而非人；协议围绕「不可变对象 + 分层缓存」设计；派生数据用一个统一的递归机制。

和 Meta Sapling 比

Sapling 由三部分组成：客户端 sl（源自 Mercurial、可操作 Git 仓库）、服务端 Mononoke、虚拟文件系统 EdenFS行业做法。它的目标是让操作随「开发者在用的文件数」扩展，而不是随仓库大小；EdenFS 在访问时才填充文件；历史用 Segmented Changelog 按需下载行业做法。

Meta 也说这需要在线，但在提交等常见流程里保留了可配置的离线能力行业做法。

推测最明显的区别是取舍的方向：Sapling 想兼顾人类开发者的体验和 Git 兼容；Scion 明确为在线的智能体优化，客户端更「瘦」，连提交都放到服务端。

原文对 Git 生态的建议

原文认为，这类问题会在未来 6–12 个月里变得常见官方。它建议 Git 生态不必放弃整体模型：Git 服务端不必和客户端一样工作；托管平台可以提供类似 Scion 的完整服务端 RPC，甚至跨平台标准化，让 Git 客户端学会调用；协商协议可以变；各种 sparse、shallow 特性可以做到能组合使用官方。他们希望和 GitHub、GitLab 及开源社区合作官方。

第 07 节

给开发者和团队的启示

现在就能做的〔建议〕

  • 先量一下「每个改动在版本控制上花多久」。Anthropic 量出来是 34 分钟。智能体越多，克隆、拉取、status 的时间越接近主要成本建议。
  • 能不克隆就不克隆。让 CI 和机器人优先用托管平台的 API 回答「谁改的、哪次改的、diff 是什么」；必须检出时，用 Git 已有的部分克隆和稀疏检出，并让同一台机器上的任务共享对象库建议。
  • 给智能体提供正确的「问路方式」。Claude 线性扫提交日志的例子说明：如果没有一个现成的、便宜的查询接口，智能体就会自己去暴力实现。把评审系统、合入记录做成可查询的工具建议。
  • 评审看意图，用规则分流。用 CODEOWNERS 之类的路径规则，加上「只改文档 / 注释」的自动判定，把人的注意力留给逻辑改动建议。

合入量真涨上去之后〔建议〕

  • 重新想合并队列。如果排队时间开始主导交付时间，考虑「合入前跑快测、合入后跑全量 + 自动 bisect/revert」。前提是你有便宜的历史查询和可靠的回滚建议。
  • 给关键组件配一个专门盯盘的智能体。superfan 的做法成本不高：一个频道、一个能读日志和遥测的 Claude、一个明确的组件范围建议。
  • 别急着自研。Anthropic 自己说，这些概念只对「上万工程师或成群智能体」的超大 monorepo 有意义，而且他们的 token 预算远超一般企业官方。大多数团队应先在 Git 体系内把服务端能力用足建议。

第 10 节

Dong 的理解（复习用）

用自己的话串一遍，回头看时先读这里。1. Git 每个 commit 是一个快照：逻辑上是完整的文件夹，物理上是一份索引——tree（文件树，每个目录一个 tree，记录"文件名 → blob 哈希 / 子目录 → 子 tree"），commit 指向根 tree。文件内容是 blob，按内容哈希存放，没变的文件直接复用。物理存储和快照索引是分开的。2. commit 还记录父提交哈希（merge 提交有两个父），所有提交串成历史链。父哈希参与计算，所以改旧提交或 rebase 会让后续哈希都变。3. Git 不存 diff：diff 是拿两个快照现算，哈希相同的子树直接跳过；blame 要沿父链一路比较，历史越长越贵。4. Scion 本质是回到中心化（类似 Google Piper）：完整历史只在服务端存一份。客户端提交的不是逐行 diff，而是 changeset（改了哪些文件 + 新内容哈希）；服务端拼出新快照，并用比较并交换（CAS）移动 main 指针官方。若 main 已被别人推进，服务端是否自动 rebase，原文未说推测。5. 本地 git 操作搬到服务端：提交、变基、合并、log、diff、blame 改由服务端执行并通过 API 提供；blame 等是递归定义的派生数据，增量计算、算一次大家共用，客户端不必拉近 100 GB 历史官方。代价：必须在线，服务端是关键依赖。6. 切分支：客户端说要哪个提交、哪些路径，文件经 daemon → 区域缓存 → 服务端三层按哈希按需取官方；更可能是拿目标树清单在本地比较、只取变化的文件，而不是服务端算好 diff 下发推测。

第 11 节

可复用的 insight

从 Scion 抽出、可迁移到其他领域的设计思路建议。1. 用户变了，就重审设计前提：Git 为「人、偶尔离线、每天提交几次」设计；换成一直在线、每天几万次提交的智能体，前提失效。给智能体用的系统都值得把隐含前提列出来逐条重问。2. 把「存什么」和「怎么看」分开：内容按哈希存一份，快照只是一份索引。数据湖、Docker 镜像分层、文档版本管理同理：不可变内容可随意缓存、去重、共享。3. 贵的计算在中心算一次，大家共用：blame 等派生数据在服务端预算并增量更新，比每人本地重算便宜得多；推荐系统特征库、知识库 embedding 同理。4. 按需取，层层缓存：不拉全量，要什么取什么，加多级缓存；内容寻址让命中率做到 99% 以上。5. 把「事前严防」换成「事后快修」：放弃合入前排队全测，改为先合入、出问题快速定位/回滚/让 Claude 修；前提是定位和回滚足够便宜。改动快且多时，可快速恢复往往比绝不出错更划算。6. 人的角色从逐行审改为把方向：评审看意图、对 Claude 说「不」；智能体产出量大后，人只能把关方向。
