第 01 节

一句话读懂

先把结论放在前面

一句话

没有标准答案时，别问「这次输出对不对」，改问「这次改 harness 有没有按预期改变同题行为」——先对照跑，再只合并有证据的改动，最后把可复用的教训写进 EXPERIENCE.md。

  1. 对象。八类文件组件（C1–C8）：系统提示、护栏、记忆、工具指南、子 Agent、Skills、脚本、插件论文。
  2. 任务级。Propose（通用+领域两候选）→ Probe（同题重跑）→ Compose（按行为证据合并）论文。
  3. 跨任务。每题结束后反思写入库；下一题仍从基础 harness H₀ 出发，只检索经验，不继承上题定制配置论文。
  4. 数字。单步最大：WorkBuddy +11.5、JobBench +4.5、LAB 部分通过率 +11.8 点；去掉经验库掉 3.1 / 1.8 分论文。
  5. 短板。依赖重跑与强 LLM 判断；编辑器与部分评分器同家族；每题成本高评论。

值得带走的是两件事：用同题对照代替标准答案，以及存「怎么改」而不是存「改成什么」评论。

阅读顺序：第 2 节看问题设定；第 3 节拆 C1–C8；第 4–5 节讲两层循环并配图；第 6 节数字；第 7–8 节批评与可复用做法；第 9–10 节术语与 Dong 的理解。

第 02 节

要解决什么问题

开放世界里，harness-RSI 容易失效的两件事

Harness 指冻结模型外面那一圈运行时脚手架：提示词、记忆、skill、工具、编排论文。作者沿用 Weng 的说法：*Agent = Model + Harness*；harnessing 就是优化这层脚手架论文。

开放任务流上有两个难点论文§1：

  1. 没有 ground-truth 验证器。写法律备忘录、改一版方案，没有「标准答案」可对；你改了一句系统提示，不知道是变好还是变坏。
  2. 任务间不能直接继承定制。为法律题调出来的 harness，下一道税务题多半不适用；把上题整包配置拷过去，容易变成噪声递归。

Harness² 的回答是两个耦合循环：任务内用对比式 Propose–Probe–Compose 改当前执行 harness；任务结束后把有证据的经验写入改进 harness 的库，指导未来如何被改进论文。权重、编辑器提示词和决策规则全程冻结；变的是每个任务的组件文件和库论文。

第 03 节

八个可编辑组件（C1–C8）

每个组件是一个文件，一次修改就是一个 diff

论文沿用 AHE 的文件级拆分并加一类；在 Codex 下常驻文本也可落在 AGENTS.md。

#组件典型文件何时进模型作用
C1系统提示systemprompt.md每次调用角色与顶层流程
C2护栏guardrails.md每次调用与任务无关的硬约束
C3记忆LongTermMEMORY.md每次调用同领域跨任务的持久事实
C4工具指南tool_descriptions/tool_guidance.md每次调用何时、如何用现有工具
C5子 Agentsub_agents/<n>/AGENT.md经 task 工具独立上下文的委派执行者
C6Skillsskills/<n>/SKILL.md（+ 脚本）调用时专门流程，加载前不占成本
C7脚本scripts/<name>.py经 bash确定性能力，替代逐 token 推理
C8插件plugin/<name>.ts工具循环内包裹工具调用的钩子（强制执行）

四组：上下文构建（C1–C3、C6）、工具接口（C4、C7）、编排（C5）、中间件（C8）论文。编辑器偏好形式顺序大致是：skill → 脚本 → 子 Agent → 插件 → 常驻文本——因为常驻文字每次都占窗口论文App.H。

第 04 节

总览：两层递归

架构图

任务级递归更新当前任务的执行 harness，信号是同题多次运行之间的行为对比论文。Harness 优化级递归在任务结束后更新库：被采纳的完整 harness + EXPERIENCE.md（情境 cue、教训 lesson、证据 evidence、置信度）论文。下一题仍从基础 H₀ 起步；早先组件经 Propose 复用或改编，从不自动继承论文§2.3。

第 05 节

Propose–Probe–Compose

流程图

Propose。先用当前 harness 跑出参考执行 e⁰——论文强调这揭示的是 *harness 如何表现*，不是交付物是否正确论文p.5。编辑器写出两个候选：

  • 通用（invariant）：规划、工具使用、上下文管理、委派等可能跨领域重复的缺陷；
  • 领域特定：该领域知识、流程与约束。

每条修改必须能追溯到轨迹中的某个时刻；说不出时刻就视为臆测论文App.H。KEEP_BASE 是可接受答案论文。

Probe。在同一任务、同一模型、同一环境下跑每个候选，做行为对比：缓解了目标缺陷、没改变行为，还是引入退化？对比用来*指导组合*，不是验证正确性论文。

Compose。组合器可读参考、候选、diff 与全部执行证据，合并有支持的改动、修订冲突、整体采纳或保留当前；每个决策挂钩观察，写成 kept | revised | dropped -> edit -> evidence论文。单次候选 rollout 是弱证据；与「什么都没产出」关联的修改默认不安全论文Prompt 3。

预算 k。并行形式控制宽度（一次种群更新）；顺序形式控制深度（串联修订）。k>1 时，盲选选择器只看匿名化交付物，不知道来自哪个 harness；被采纳记为 H★——「是采纳，而非经过验证的最优」论文p.6。

经验写入。反思器对每项改动判 helped / hurt / no observed effect / confounded，至多一条持久经验；没有可复用对比就 NO_ENTRY论文。关键在于：被选择器选中 ≠ 其中每个修改都有功——胜出者里可能混着无关改动论文。

第 07 节

批评与边界

「没有 ground truth」实际靠什么

评论替代验证器的是：当前任务重跑、每组 n=1 的行为对比、结构化 LLM 选择器、保守反思器。论文失败分析（App.E.6）显示：盲选可能选 55 分丢掉 95 分；选择器可能偏好「精确但窄」的 LAB 答案导致分数大跌；编辑器自写检查脚本三次报 PASS，却漏掉隐藏测试假设。

同家族评判

JobBench 由 Claude Opus 4.8 评分，与编辑器同模型；LAB 由 Claude Sonnet 4.6 评分论文。评论部分提升可能是编辑器把交付物推向自家族偏好；独立家族重评是首要复核项。

成本与安全

推测/读图k=1 约数次执行+数次强模型会话；k=5 并行可达约 20 次执行量级。适合高价值交付物，不适合每条聊天。官方仓库注明执行器网络受限弱、Codex 可关 sandbox；编辑器会写 bash 脚本与 TS 插件且无人工审查——业务环境需沙箱与审查论文App.D/H；评论。

库只增不减

任务级 harness 用完可丢；风险在库：错误规则可能传给下一题。整合、遗忘列为未来工作论文App.G。第三方报道提醒自动加组件易过度工程。

第 08 节

可复用做法〔建议〕

现在就能抄的

  1. 两个分工编辑器 + 组合器，决策写成 kept|revised|dropped -> edit -> evidence。
  2. 修改必须挂钩轨迹时刻；优先修多次运行间的分歧；优先 skill/脚本而非常驻文本；允许 KEEP_BASE。
  3. 目录树校验器：被引用的 skill/脚本必须存在，坏树拒绝或回退。
  4. 工作区防护：编辑器目录里绝不放答案要点、评分细则或分数。
  5. 反思格式：逐项 helped/hurt/no effect/confounded；至多一条含 cue/lesson/evidence/confidence 的经验，否则 NO_ENTRY。
  6. 库条目 = 可执行 harness（或 diff）+ EXPERIENCE.md + 索引；新任务从基础配置再检索。
  7. 事实与流程分离：仓库事实进按仓库缓存；只有流程进共享 skill。

暂时别照搬

  • 对每个真实请求做 k=5；先 k=1。
  • 把盲选选择器当最终裁决；先过你自己的硬关口。
  • 把编辑器写的检查器当证据。
  • 未经审查的 LLM 钩子；可编辑的硬性契约（INVARIANTS）。
  • 无上限的经验库。

第 10 节

Dong 的理解〔讨论〕

用自己的话串一遍，回头先读这里。

  1. 改的是文件，不是权重。八个组件都是可 diff 的文本/脚本；模型 M 固定。
  2. 没有标准答案时，用同题 A/B。问的是「改动有没有改变它声称要改的机制」，不是「输出得分多少」。
  3. 通用候选 vs 领域候选再组合，比一次大反思重写更可控；每个决策要留证据链。
  4. 跨任务只传经验，不传整包定制 harness，避免把上题特化配置焊死到下题。
  5. 库是「改进者」真正会变的部分；编辑器提示词本身冻结——所以叫「改进改进者」时别理解成 Hyperagents 那种改元流程。
  6. 对 module-explainer / skill RSI：把 PPC 当变异算子，把自有 L0–L1 关口当接受门；EXPERIENCE 格式可直接用；编辑器与评判器尽量不同家族。
  7. 别把头条 +11.5 当成「无验证器魔法」——背后是重跑、强编辑器和（部分）同家族评判；先做 k=1 与 Best-of-k 对照。
